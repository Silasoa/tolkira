# Design

## Context

The report and print view ship; the stable `ReportSummary` already carries the
status, counts, duration, attachments and scenarios. The email is a second,
opt-in artifact built from that summary: no SMTP, no network, no server and no
new dependency. The one-file report default is unchanged. The first slice is a
standalone HTML email body (`.html`) with inline styles and a table layout, not
an `.eml` draft; the `.eml` option is a follow-up. The user sends or pastes the
HTML.

Data flow: the CLI parses `--email` and the existing inputs -> `summarizeReport`
when there is no `--out`, or `generateReport` when there is -> `renderEmail`
(summary, title, locale, report name, validated accent, now) -> one HTML string
-> `writeAtomic` after the report/summary -> the existing JSON/CI output. The
API returns the same string; it writes nothing. The first slice embeds no
logo and no image; the accent is validated with the existing accent rule.

## Email content

- **Subject/heading:** the resolved title plus the overall status
  (`{title} — {status}`); the `<title>` and the visible heading use it. The
  first slice has no hidden preheader: the HTML body is pasted or attached, so
  a hidden preview element is not delivered and is omitted. The subject is not a
  mail header; the user types it or copies the heading (the `.eml` follow-up
  would carry a real subject).
- **Header:** the title, the status pill, the generated date (UTC,
  translator-formatted, labelled "Generated") and an optional accent border.
  No logo or image.
- **Metrics:** attempted pass rate via the existing `passRate()` helper and
  `t.percent` (one decimal, `—`/`format.noAttempts` at zero attempts, the empty
  ratio for no scenarios); every non-zero scenario status plus the unexecuted
  count; the total labelled as executed scenarios with results; features;
  steps; duration; inline attachment count and bytes. German values use the
  translator's number, percent and duration helpers.
- **Failed list:** up to five scenarios with status `failed`, each with the
  feature, scenario, status and duration; no step bodies, tags or attachments.
  Further failures are a count. The no-failure copy keys off the overall
  `summary.status`, so an undefined/pending/unknown run is not called
  successful; an empty run shows the empty state.
- **Report note:** with `--out`, the basename of the report (`run.html`) and
  "attach or share the full report"; no directory or absolute path. Without
  `--out`, "no full report was generated; run with --out for the full report".
  No URL; the email works offline and does not link to a server.
- **Footer:** generated by Tolkira; one file, no telemetry; no tracking pixel or
  remote image.

## Template

- A full HTML document with `<html lang dir>`, a `<title>`, and a 600 px
  table-based body with inline styles; a small `<style>` block for the mobile
  width and forced-colour fallback. No flex/grid, no scripts, no hidden
  preheader, no external stylesheet, font, image or link; system font stacks;
  the validated accent as a border/colour; status colours with sufficient
  contrast. `width:100%;max-width:600px` (not a fixed `width="600"`).
- Email clients strip `<style>` and scripts; the inline table layout carries the
  content. There is no image at all in this slice; the brand text is the header.
  The browser preview at 600/320 px is the visual test; real mail clients are
  documented as not covered. The standard email SHOULD stay under 100 KB.
- The HTML escapes the title, feature/scenario names, the report name and every
  catalog value; the summary values stay inert. No `.eml` headers exist, so
  there is no header injection surface in this slice; the subject in the
  `<title>` is escaped.

## CLI and API

- `--email` is composable like the other outputs: alone, with `--out`, with
  `--json`/`--ci`, or both. This matches the MCHR/Allure HTML-email pattern and
  the CI mail-step model (subject + HTML body + report attachment). The CLI
  usage and `Without --out, --json, --ci or --email` rule change; the JSON/CI
  text stays English.
- `--locale` is accepted with `--out` or `--email`; with only `--json`/`--ci` it
  stays a usage error. The email uses the report locale; the report and email
  share the title. The history still requires `--out`; the `--logo` requires
  `--out` and stays report-only; the email uses the validated `--accent` even
  standalone and has no logo.
- Path validation uses `samePath`/resolved comparisons against inputs, the
  logo, `--out`, `--ci-out` and `--history`; the email is not an input file and
  the `.html` is not collected as one. The write order is report, email,
  history, `--ci-out`, stdout. A write failure exits 1, names the email path
  (not the temp name), keeps the report and does not write the history/`--ci-out`
  or print the JSON/CI stdout; no partial email remains. When stdout is free,
  the CLI prints `Email written to <path>`; with `--json`/`--ci` the machine
  stdout is unchanged.
- `renderEmail(summary, options)` returns the HTML; `EmailOptions` are
  `title`, `locale`, optional `reportName`, validated `accent` and a `Date`
  `now`. Export it from `src/index.ts` and document it in
  `docs/AGENT-INTERFACE.md`. The CLI and API produce identical HTML for the
  same inputs.

## Localization

Add the email keys to `en.json`/`de.json` (English with descriptions, German
values): subject, status/heading, metrics labels (including every non-zero
status and unexecuted), pass-rate note, failed list, further failures, no
failures, empty run, report note (with and without a report), generated date,
footer. Use the existing `status.*` keys and `format.noAttempts`/`format.emptyRatio`
where they fit. The email uses `createTranslator(locale)` and `lang`/`dir`;
test data and the default title `Tolkira report` stay verbatim. The CLI, JSON and
CI remain English. The German email copy follows the neutral term sheet; ILA
reviews it. The no-preheader decision is documented.

  attempted pass rate incl. zero, top five/further failures, no failures and
  empty run, undefined/pending/unknown status, escaped title/names, report note
  with/without `--out`, German/English labels, numbers/duration/date,
  `lang`/`dir`, no scripts/remote assets/images, validated/hostile accent,
  documented size (<100 KB), a pinned clock, the `renderEmail` API and CLI
  parity.
- `test/cli-email.test.ts`: email with `--out`, standalone, with `--json` and
  `--ci`, `--locale` without `--out`, empty path, collisions with
  inputs/logo/out/ci-out/history, write failure (email path is a directory; no
  .tmp) leaves the report and skips history/CI, confirmation line, no flag
  leaves files untouched, the report/JSON bytes unchanged.
- `test/e2e/email.spec.ts`: open the generated email from disk at 600 and
  320 px; assert the title/status/metrics/failed list/report note, German
  labels, escaped names, no horizontal overflow, no request, and no script; use
  an email-aware helper.
- `test/i18n-catalog.test.ts` covers the new keys through the existing
  parity/placeholder/plural checks; the email keys are sorted and described.
- Fixtures: the existing summary/report inputs; the all-statuses fixture for
  undefined/ambiguous, a hostile-name summary; an empty/no-failure summary; a
  German summary. No new large fixture.

## Alternatives considered

- **`.eml` draft:** a real subject and a directly openable mail; deferred
  because of MIME/header sanitisation and client differences. The HTML body is
  the smallest complete slice.
- **Logo in the email:** omitted. The report logo can be a 2 MB data URI, which
  Gmail/Outlook clip or strip and which breaks the "small summary" promise; a
  small capped logo is a follow-up.
- **Hidden preheader:** omitted; the HTML body is pasted or attached, so a
  hidden preview element is not delivered. The heading is the subject.
- **Aggregate-only email:** smaller, but reuses no failed-scenario context; the
  top-five list is the useful summary. The user confirms the content.
- **SMTP/sending and metadata:** out of scope and against the local/no-telemetry
  baseline; `--meta` in the email is a backlog trigger.
- **Embed the full report or screenshots:** too large for mail; the report is
  attached/shared separately.
- **A server-hosted summary:** out of scope; the email works offline.
- **PDF engine:** #13c, with an ADR.

## Risks

- Mail clients vary in CSS support; the table/inline layout, no-image and
  no-remote rules are the guard, and mail-client preview is documented as not
  covered.
- The email contains feature/scenario names (opt-in, user-sent); there is no
  redaction mode. The docs say so; a future flag can omit test data.
- The HTML body has no automatic mail subject; the user copies the heading. The
  `.eml` follow-up can remove that step.
- The summary-only email has no report to attach; the note says so. The
  attachment metric is inline-only because `summarizeReport` does not carry the
  skipped-attachment count.
- The email and report share the title/locale; switching `--locale` between runs
  changes the email chrome but not the test data.
- The generated timestamp is the email generation time, not the run start; it is
  labelled "Generated".
- New catalog keys must stay in parity and the German copy needs the native
  review; the email layout needs the browser/e2e viewport tests.
- The `--json`/`--ci` composition pins the write-order contract; an email
  failure suppresses the later history, `--ci-out` and stdout outputs while the
  report stays.
