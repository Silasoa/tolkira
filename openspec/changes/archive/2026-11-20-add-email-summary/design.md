# Design

## Context

The report and print view ship; the stable `ReportSummary` already carries the
status, counts, duration, attachments and scenarios. The email is a second,
opt-in artifact built from that summary: no SMTP, no network, no server and no
new dependency. The one-file report default is unchanged. The first slice is a
standalone HTML email body (`.html`) with inline styles and a table layout, not
an `.eml` draft; the `.eml` option is a follow-up. The user sends or pastes the
HTML.

Data flow: the CLI parses `--email` and the existing inputs -> `summarizeReport`
when there is no `--out`, or `generateReport` when there is -> `renderEmail`
(summary, title, locale, report name, validated accent, now) -> one HTML string
-> `writeAtomic` after the report/summary -> the existing JSON/CI output. The
API returns the same string; it writes nothing. The first slice embeds no
logo and no image; the accent is validated with the existing accent rule.

## Email content

- **Subject/heading:** the resolved title plus the overall status
  (`{title} — {status}`); the `<title>` and the visible heading use it, and the
  heading is the suggested subject. The first slice has no hidden preheader: the
  HTML body is pasted or attached, so a hidden preview element is often dropped
  and is deferred to a sending or `.eml` follow-up. The subject is not a mail
  header; the user types it or copies the heading (the `.eml` follow-up would
  carry a real subject).
- **Header:** the title, the status pill, the generated date (UTC,
  translator-formatted, labelled "Generated") and an optional accent border.
  No logo or image. The `Tolkira` eyebrow is the first visible line.
- **Metrics:** attempted pass rate via the existing `passRate()` helper, shown as
  a percentage with the full `email.passRateNote` sentence that skipped scenarios
  are not attempts, plus `format.noAttempts` and the unexecuted count for an
  all-unexecuted run and the empty ratio for no scenario rows. The empty run and
  the all-unexecuted run are distinct states; the attempted-only note and failed
  section are hidden only for a run without scenario rows. Every non-zero
  scenario status plus the unexecuted count; the total labelled as executed
  scenarios with results; features; steps; duration; the inline-attachment count
  labelled "Attachments in the run" plus bytes. English digits are grouped
  (`8,509`) and durations use `12 ms`, `12.3 s`, `1 min 5 s` or `1 h 2 min`
  through email-local helpers; German values use the locale number/percent
  formatting and the same email-local duration form. The report helpers and JSON
  numbers are unchanged.
- **Failed list:** the first five failed scenarios in summary order, each with
  the feature, scenario, status and duration; no step bodies, errors, tags or
  attachments. The heading, note and failed names use `overflow-wrap:anywhere`;
  displayed feature, scenario and report-name strings are capped at 200
  characters with an ellipsis. Further failures are a count. The no-failure copy
  keys off the overall `summary.status`, so an undefined/pending/unknown run is
  not called successful; an empty run shows the empty state.
- **Report note:** with `--out`, the basename of the report (`run.html`) and
  "attach or share the full report"; no directory or absolute path. Without
  `--out`, a recipient-facing note says that no full report is attached. No CLI
  instruction, path or URL; the email works offline and does not link to a
  server.
- **Footer:** generated by Tolkira; one file, no telemetry; no tracking pixel or
  remote image.

## Template

- A full HTML document with `<html lang dir>`, a `<title>`, and a 600 px
  table-based body (`width:100%;max-width:600px`, not a fixed `width="600"`) with
  inline styles and an inline system font stack; a small `<style>` block for the
  width below 480 px and the forced-colour fallback, so 600 px keeps the 2 by 2
  metric grid. No flex/grid, no scripts, no hidden preheader, no external
  stylesheet, font, image or link; the validated accent as a border/colour;
  status colours with sufficient contrast.
- Email clients strip `<style>` and scripts; the inline table layout carries the
  content. Long text wraps anywhere and displayed names are capped at 200
  characters with an ellipsis; the status pill keeps its count and label
  separated. There is no image at all in this slice; the brand text is the
  header. The browser preview at 600/320 px is the visual test; real mail clients
  are documented as not covered. 600 px keeps the 2 by 2 metric grid; only the
  width below 480 px stacks it. A standard email SHOULD stay under 100 KB.
- The HTML escapes the title, feature/scenario names, the report name and every
  catalog value; the summary values stay inert. No `.eml` headers exist, so
  there is no header injection surface in this slice; the subject in the
  `<title>` is escaped.

## CLI and API

- `--email` is composable like the other outputs: alone, with `--out`, with
  `--json`/`--ci`, or both; `--ci-out` still requires `--ci markdown`. This
  matches the MCHR/Allure HTML-email pattern and the CI mail-step model (subject
  + HTML body + report attachment). The CLI usage and
  `Without --out, --json, --ci or --email` rule change; the JSON/CI text stays
  English.
- `--locale` is accepted with `--out` or `--email`; with only `--json`/`--ci` it
  stays a usage error. The email uses the report locale; the report and email
  share the title. `--title` sets the email heading/suggested subject and
  `--accent` the top border, even standalone; the history still requires
  `--out`; the `--logo` requires `--out` and stays report-only; the email has no
  logo.
- Path validation uses `samePath`/resolved comparisons against inputs, the
  logo, `--out`, `--ci-out` and `--history`, and rejects a path inside an input
  directory even when it does not exist yet; the email is not an input file and
  the `.html` is not collected as one. The write order is report, email,
  history, `--ci-out`, stdout. A write failure exits 1, names the email path
  (not the temp name), keeps the report and does not write the history/`--ci-out`
  or print the JSON/CI stdout; no partial email remains. When stdout is free,
  the CLI prints `Email written to <path>`; with `--json`/`--ci` the machine
  stdout is unchanged.
- `renderEmail(summary, options)` returns the HTML; `EmailOptions` are
  `title`, `locale`, optional `reportName`, validated `accent` and a `Date`
  `now`. Export it from `src/index.ts` and document it in
  `docs/AGENT-INTERFACE.md`. The CLI and API produce identical HTML for the
  same inputs.

## Localization

Add the email keys to `en.json`/`de.json` (English with descriptions, German
values): subject, status/heading, metrics labels (including every non-zero
status and unexecuted), the pass-rate note, failed list, further failures, no
failures, empty and all-skipped runs, report note (with and
without a report), generated date, footer. Use the existing `status.*` keys,
`format.noAttempts` and `format.emptyRatio` where they fit. The email uses `createTranslator(locale)` and `lang`/`dir`; English
email digits are grouped (`8,509`) and durations use email-local human forms
(`12 ms`, `12.3 s`, `1 min 5 s`, `1 h 2 min`), while the report helpers and JSON
numbers are unchanged. Test data and the default title
`Tolkira report` stay verbatim. The CLI, JSON and CI remain English. The German
email copy follows the neutral term sheet; the recipient-facing notes are
`Vollständiger Bericht: {name}. Bitte separat anhängen oder teilen.` and
`Es ist kein vollständiger Bericht angehängt.`. ILA reviews it and a guard test
rejects an English fallback in the German note. The no-preheader decision is
documented.

  attempted pass rate incl. zero and the full pass-rate note, the empty vs
  all-skipped state, first five/further failures in summary order, no failures,
  undefined/pending/unknown status, escaped title/names, report note
  with/without `--out`, German/English labels, grouped English numbers and human
  durations, dates, `lang`/`dir`, long-name wrap/cap, no scripts/remote
  assets/images, validated/hostile accent, the <100 KB standard size, a pinned
  clock, the `renderEmail` API and CLI parity.
- `test/cli-email.test.ts`: email with `--out`, standalone, with `--json` and
  `--ci`, `--locale` without `--out`, empty path, collisions with
  inputs/logo/out/ci-out/history and an input directory, write failure (email
  path is a directory; no .tmp) leaves the report and skips history/CI,
  confirmation line, no flag leaves files untouched, the report/JSON bytes
  unchanged.
- `test/e2e/email.spec.ts`: open the generated email from disk at 600 and
  320 px; assert the title/status/metrics/failed list/report note, German
  labels, escaped names, no horizontal overflow, no request, and no script; use
  an email-aware helper.
- `test/i18n-catalog.test.ts` covers the new keys through the existing
  parity/placeholder/plural checks; the email keys are sorted and described.
- Fixtures: the existing summary/report inputs; the all-statuses fixture for
  undefined/ambiguous, a hostile-name summary; an empty/no-failure summary; a
  German summary. No new large fixture.

## Alternatives considered

- **`.eml` draft:** a real subject and a directly openable mail; deferred
  because of MIME/header sanitisation and client differences. The HTML body is
  the smallest complete slice.
- **Logo in the email:** omitted. The report logo can be a 2 MB data URI, which
  Gmail/Outlook clip or strip and which breaks the "small summary" promise; a
  small capped logo is a follow-up.
- **Hidden preheader:** deferred; the HTML body is pasted or attached, where a
  hidden preview element is often dropped. The heading is the subject.
- **Aggregate-only email:** smaller, but reuses no failed-scenario context; the
  first-five failed list is the useful summary. The user confirms the content.
- **SMTP/sending and metadata:** out of scope and against the local/no-telemetry
  baseline; `--meta` in the email is a backlog trigger.
- **Embed the full report or screenshots:** too large for mail; the report is
  attached/shared separately.
- **A server-hosted summary:** out of scope; the email works offline.
- **PDF engine:** #13c, with an ADR.

## Risks

- Mail clients vary in CSS support; the table/inline layout, no-image and
  no-remote rules are the guard, and mail-client preview is documented as not
  covered.
- The email contains feature/scenario names (opt-in, user-sent); there is no
  redaction mode. The docs say so; a future flag can omit test data.
- The HTML body has no automatic mail subject; the user copies the heading. The
  `.eml` follow-up can remove that step.
- The summary-only email has no report to attach; the recipient-facing note says
  so and never points at a missing file. The attachment metric is inline-only
  because `summarizeReport` does not carry the skipped-attachment count.
- The title is included and may carry a branch or build name; the docs say so.
  The report basename is the only path-like content.
- The email and report share the title/locale; switching `--locale` between runs
  changes the email chrome but not the test data.
- The generated timestamp is the email generation time, not the run start; it is
  labelled "Generated".
- New catalog keys must stay in parity and the German copy needs the native
  review; the email layout needs the browser/e2e viewport tests.
- The `--json`/`--ci` composition pins the write-order contract; an email
  failure suppresses the later history, `--ci-out` and stdout outputs while the
  report stays.
