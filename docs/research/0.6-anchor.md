# 0.6 anchor research: baseline comparison

Research note, 2026-11-23. Question: is a baseline diff against an earlier run
summary the right spine for a substantial 0.6.0, and what exact shape should it
take? Method: read the governance and product docs, the history and summary
implementations, the history tests, the prior research notes, and checked the
open-issue list. No code, test or OpenSpec change was made.

## Verdict

**Keep the anchor, but restate it: a baseline comparison against a previous
`--json` summary, not a diff against the history sidecar.** The history sidecar
is aggregate-only by contract and cannot supply per-scenario identity or status
(`src/history.ts:13`, `:14-31`; `docs/AGENT-INTERFACE.md:422-426`). "Extend
Trends" is therefore not a smaller version of this feature; it is a different,
larger storage change. "Point `--baseline` at the previous summary" is the
smallest honest version and the one the archived research already recommended
(`docs/research/archive/indirect-report-patterns.md:984`).

Recommend **scope B**: report + JSON + one CI line, sourced from an explicit,
read-only baseline file. It is one coherent feature, it serves humans, CI and
agents, it forces the stable identity the report needs anyway, and it adds no
new persistence. It does add new report content: the names of baseline scenarios
that are not in this run become part of the HTML, so the report should be
treated like the current run's report (one baseline per suite/variant, no
untrusted report exchange). Scope C (per-scenario history over 30 runs) is a
different product and should not ship in 0.6.

Two honest caveats. First, direct user demand for history is thin: one research
note explicitly says **"Do not spend: ... the history baseline"**
(`docs/research/reporting-feature-requests.md:62`) and another calls a history
file **"a reasonable later feature, not the first screen"**
(`docs/research/reporter-users.md:460-462`). The anchor is a bet on mature-tool
expectations and on the user's "substantial 0.6" requirement, not on the 395
issue titles. Second, if the user rejects the baseline-artifact lifecycle, the
strongest one-run alternative in the archived shortlist is the **failure-cause
view** (ranked second in `indirect-report-patterns.md:981`); it has weaker
direct demand, but it is smaller and has no second file.

The anchor is therefore a product bet: 0.6 needs one large, coherent capability,
and this is the largest capability that fits the one-file, offline, no-server

## 2. What exists today

### 2.1 History sidecar, schema 1

| Fact | Reference |
| --- | --- |
| Schema version `1`, 30-run limit, 1 MiB cap, 200-character title cap | `src/history.ts:7-11` |
| Entry fields: `id`, `recordedAt`, `title`, `status`, feature/scenario/step counts, `durationMs`, attachment totals, optional `flaky` | `src/history.ts:14-31` |
| Aggregate-only comment: "no scenario names or steps" | `src/history.ts:13` |
| `id` is a SHA-256 of the aggregates plus title, excluding time; identical last run dedupes | `src/history.ts:200-233` |
| Reader: missing file is empty; non-regular file, oversize, wrong schema, bad fields and inconsistent counts are rejected without a rewrite | `src/history.ts:261-308` |
| Writer: atomic, trailing newline, bounds to 30 and caps titles | `src/history.ts:314-332` |
| CLI: `--history` requires `--out`, is read before generation and written after the HTML | `src/cli.ts:40`, `:419-445`, `:540-543`, `:582-599` |
| Documented contract and limits | `docs/AGENT-INTERFACE.md:345-445`, `:683-691`; `docs/ARCHITECTURE.md:26-31`; `docs/LIMITATIONS.md:15` |
| No scenario-level history, no dashboard, no revision | `docs/AGENT-INTERFACE.md:422-426`; `docs/BACKLOG.md:330-338` |

The sidecar deliberately stores no names, paths, tags or step text. That is the
privacy property that makes it safe to embed in a shared HTML file. It also
makes it unusable as a scenario baseline: you cannot label a new failure from a
pass-rate row.

### 2.2 Summary, schema 2

| Fact | Reference |
| --- | --- |
| Schema version `2`; breaking changes bump it | `src/summary.ts:21`; `docs/AGENT-INTERFACE.md:551` |
| Scenario fields: `name`, `uri`, `feature`, `status`, `executed`, `durationMs`, `attempt`, `tags`, `attachments`, `steps` | `src/summary.ts:47-59`, `:287-298` |
| No `recordedAt`, title, line, rule/describe, or example identity | schema example `docs/AGENT-INTERFACE.md:447-503` |
| Sorted by URI then name; duplicate names are allowed | `src/summary.ts:301-303`; `docs/AGENT-INTERFACE.md:575` |
| Example rows can share a pickle name; the HTML labels them `#1.1`, "but the summary does not expose them yet" | `docs/AGENT-INTERFACE.md:576-580`; `src/render/report.ts:219-221`, `:386-390` |
| Never-started pickles are pruned from report and summary; a started-but-unexecuted row remains with `executed: false` and `status: "unknown"` | `src/summary.ts:196-198`; `src/report/model.ts:578-582`; `docs/AGENT-INTERFACE.md:566-571`, `:648` |
| URIs are reduced to a display form (`features/...` or the last three path segments) and absolute paths are dropped | `src/summary.ts:155-174` |

### 2.3 Report identity today

- DOM ids are positional: `scenario-<featureIndex>-<scenarioIndex>`
  (`src/render/dom-contract.ts:27-29`). Adding a feature or scenario breaks every
  old anchor. That is the deep-link problem the archived note ranks fourth
  (`indirect-report-patterns.md:983`).
- Rows carry `data-uri`, `data-scenario-name`, `data-tags`, `data-search` and,
  for outline rows, `data-example` / `data-examples-name`
  (`src/render/dom-contract.ts:31-58`; `src/render/report.ts:449-460`). These are
  presentation facts, not a durable identity.
- The report model has the outline coordinates (`examplesIndex`, `exampleIndex`)
  and the line, but the summary does not (`src/report/model.ts:729-744`,
  `:751-772`).

### 2.4 What a user can do today

- See aggregate trends from the second run: pass rate, passed/failed/skipped/
  total, flaky count/share and duration; the tab only exists with two or more
  entries (`src/render/html.ts:44-45`, `:90`; `src/render/trends.ts:184-193`;
  `test/render-trends.test.ts:124-149`).
- See earlier attempts inside the current run (report only) for retried
  scenarios (`docs/AGENT-INTERFACE.md:268-275`).
- Diff two `--json` files externally with `jq`/`comm`, but with no identity
  contract: outline examples and duplicate names collide, and the summary has no
  run title or time.
- Nothing in the tool reads a previous summary, matches scenarios, or labels a
  failure as new/fixed. There is no `--baseline` flag, no summary reader and no
  cross-run scenario storage.

So the anchor is **not** "80% already shipped". Only the current-run summary and
the rendering/CI infrastructure are reusable. The new work is the baseline
reader, the identity/matcher, the summary extension, the report surface and the
docs/tests.

## 3. Identity

### 3.0 There is no cross-run matching today

The only cross-run mechanism in the code is the history entry `id`: a SHA-256 of
the whole-run aggregates plus title, used to dedupe a repeated run
(`src/history.ts:200-224`). It never identifies a scenario. Within one run, a
scenario is keyed by the producer's `pickle.id` (`src/report/index-run.ts:69`,
`:202`), which is not stable across runs. The summary lists `feature`, `name`,
`uri`, `tags` and step text (`src/summary.ts:47-59`), but nothing compares them
to a previous run. CI annotations use feature + scenario name + first failure
message as a display identity and explicitly admit that duplicates are
indistinguishable (`docs/CI.md:80-83`).

Step text is the weakest candidate of all: it changes whenever the test changes,
which is exactly the event a baseline should report as a change, not as a new
identity. It should not be part of the key. The practical candidates are feature
name, scenario name, the example coordinate and the URI, assessed below.

### 3.1 What can and cannot be the key

| Candidate | Stable across runs? | Verdict |
| --- | --- | --- |
| Pickle id / AST node id | No; generated per run | Never use |
| Array index / row position | No; changes on insert/remove; the report uses it only for DOM ids/position, not as a durable identity | Never use (`indirect-report-patterns.md:983`) |
| Line number | No; moves when anything above it changes; absent from the summary | No |
| Feature URI | Changes on file rename/move; display-normalised and lossy; two roots can collapse to the same `features/...` | Tie-breaker only |
| Tags | Change with suite policy, not identity | No |
| Feature name + scenario name | Survives file renames and input reordering; user-authored | **Base key** |
| Examples block + row coordinate | Distinguishes outline rows that share a name; the report already computes it | **Refinement** |

The collision is real, not theoretical. In
`test/fixtures/messages/examples-tables.ndjson:4-7`, four pickles from one
outline all carry the name `Eating cucumbers`; in
`test/fixtures/messages/examples-tables-attachment.ndjson:4-5`, both rows are
`Attaching images in an examples table`. A schema-2 summary of either run
contains four/two rows with identical `feature`, `uri` and `name`.

### 3.2 Proposed smallest stable identity

Match in this order, deterministically:

1. **Base key:** `feature name` + `scenario name`.
2. If the base key is unique in both runs, it is the match. This is the common
   case and keeps old baselines usable.
3. If the base key repeats, refine with the **example coordinate**
   (`examplesIndex` + `exampleIndex` within the outline) when both sides carry
   it. Then, if still repeated, refine with the **display URI**.
4. If a group remains repeated after both refinements, mark the whole group
   **identity ambiguous**, exclude it from the tracked change counts, and state
   the count in the report/JSON. Do not pair by order, status or "closest name".
5. Do not claim "modified". A renamed feature or scenario is a removed row plus
   a new row; the archived note explicitly rejects inferred "modified"
   (`indirect-report-patterns.md:967`).

The only summary addition this needs is the example coordinate on outline rows
(for example `examplesIndex` and `exampleIndex`, or the already rendered
`example: "#1.1"` label). It must be emitted for every outline row, with or
without a baseline, so the next run's baseline carries it. It is additive, so
schema 2 stays 2, following the precedent of `steps[].suggestions` and
`steps[].definitions` (`docs/AGENT-INTERFACE.md:606-612`). A baseline written by
0.5 has no coordinate: its unique names still match; its repeated names become
ambiguous rather than silently wrong. That is the right upgrade behaviour.

### 3.3 What "removed" can honestly mean

The summary cannot distinguish three cases: a scenario deleted from the feature
file, a scenario never started in this run, and a scenario excluded by a shard
or a tag filter. Never-started pickles are pruned
(`src/summary.ts:196-198`; `docs/AGENT-INTERFACE.md:648`), and a sharded run
contains only its shard. Therefore:

- Use **"not in this run"** in user copy, not "removed" as a claim of deletion.
- Require one baseline per suite and variant, mirroring the history rule
  (`docs/AGENT-INTERFACE.md:425-426`).
- For sharded runs, compare the merged run, never an individual shard
  (`docs/CI.md:227-310`). A shard baseline would mark every other shard's
  scenarios as not in this run.
- Do not count a scenario that moved from failed to skipped as fixed or not in
  this run; it is simply not executed now. Only the explicit transitions below
  are claimed.

### 3.4 Optional second benefit: stable deep links

The same key can back stable anchors, because the current `scenario-1-1` ids
break on insertion (`src/render/dom-contract.ts:27-29`). I would keep this out
of the 0.6 baseline change unless it is nearly free: changing the existing ids
breaks bookmarks and tests, and adding a second id needs a copy-link decision.
The identity module should be reusable for that later.

## 4. Three candidate scopes

### A — report-only baseline diff

Contents: `--baseline <summary.json>`, the same additive example coordinate on
outline rows (the baseline needs it), the matcher, a compact "Compared with
baseline" panel and per-row badges in the HTML. No `baseline` block in the
summary and no CI change. Size: **M**. Risk: medium (identity edges, new report
surface), but contained. Value: humans only; agents and CI would still have to
scrape the HTML or reimplement matching, which contradicts
`docs/AGENT-INTERFACE.md:13-15`.

### B — diff plus JSON and CI output (recommended)

Contents: everything in A plus an additive `baseline` block in the schema-2
summary (and a per-scenario `change` when a baseline is supplied) and one
deterministic CI line, for example
`Baseline: 2 new failures · 1 fixed · 3 still failing · 1 not in this run`.
The `baseline` block appears only with `--baseline`. The only unconditional
summary change is the additive example coordinate on outline rows (needed so the
next baseline can match them), so summary goldens change for outlines; the CI
bytes are unchanged without the flag. The report should aim for byte-identical
HTML without the flag by reusing existing styles; if a new CSS rule is
unavoidable, measure the always-on delta and record it. Size: **L** (roughly
1,500-2,500 changed lines including tests, fixtures, docs and catalog keys).
Risk: medium-high (new untrusted file reader, schema discipline, conditional CI
bytes). Value: humans, CI and AI agents from one diff; the feature becomes a
contract instead of a view.

### C — diff plus history-wide trends

Contents: B plus per-scenario persistence across the 30-run window: first seen,
fail streak, added/fixed over time, per-scenario trends. Size: **XL**. Risk:
high. It requires a new persistence schema (the current sidecar is 1 MiB,
aggregate-only, schema 1), a privacy decision to store scenario names/URIs in a
shared sidecar, retention and migration, and a much larger test/host matrix. It
also answers a different question ("how has this scenario behaved over 30
runs?") than the one the anchor promises ("what changed since the last run?").
Not 0.6.

### Recommendation

**B**, with these deliberate exclusions:

- **No automatic writer.** The baseline is the user's existing `--json`
  artifact, read-only. The CLI keeps its "only the CLI writes history" rule and
  the report keeps one optional sidecar.
- **No change without the flag.** Add a characterization test that a run
  without `--baseline` has byte-identical CI output and no `baseline`/`change`
  keys in JSON; the only summary delta is the additive example coordinate on
  outline rows. The HTML must carry no baseline data and no visible change
  (ideally byte-identical by reusing existing styles).
- **A path rule, not a silent skip.** Reject a baseline that is an input file or
  lives inside an input directory, even when the file does not exist yet, and
  reject a collision with the logo or any output. Excluding it from the input
  scan instead would make a real input disappear silently. `--baseline` also
  needs a surface that shows it (`--out`, `--pdf`, `--json`, `--ci`); an
  email-only run is a usage error rather than a silent no-op.
- **No email/PDF-specific work.** The PDF inherits the report panel; the email
  stays a concise current-run summary in this slice.
- **No new filter/preset.** The panel lists the changed scenarios (with a cap)
  and the rows carry badges; a "new only" filter can wait for a user request.
- **No GitHub/Azure annotation change in the first slice.** The Markdown line
  is enough; annotations keep their current bytes and caps.

### Proposed outcome classification

| Baseline | Current | Class | Claim |
| --- | --- | --- | --- |
| absent | failing (`failed`/`undefined`/`ambiguous`) | **new failure** | Yes |
| absent | passed or non-failing | added, not failing | Informational only |
| failing | passed | **fixed** | Yes |
| failing | failing | **still failing** | Yes |
| failing | skipped/pending/unknown | other transition | No claim |
| any present | absent | **not in this run** | Yes |
| passed | skipped/pending/unknown | other transition | No claim |
| passed | passed | unchanged | No |
| passed | failing | **new failure** | Yes |

The tracked classes are disjoint: an added failing scenario is counted as a new
failure, not as added, and an added skipped/pending scenario is "added, not
failing". A run-level hook failure has no scenario row; expose the
baseline/current overall status in the `baseline` block but do not invent a
scenario for it.

An illustrative JSON excerpt (names are a proposal, not a frozen contract; the
block appears only with `--baseline`; the rest of the schema-2 document is
unchanged):

```json
{
  "schemaVersion": 2,
  "status": "failed",
  "baseline": {
    "status": "passed",
    "counts": {
      "newFailures": 2,
      "fixed": 1,
      "stillFailing": 3,
      "notInThisRun": 1,
      "added": 4,
      "ambiguous": 0
    },
    "notInThisRun": [
      {
        "feature": "Checkout",
        "name": "pays by card",
        "uri": "features/checkout.feature",
        "status": "failed"
      }
    ]
  },
  "scenarios": [
    { "name": "pays by card", "change": "new-failure" }
  ]
}
```

The per-scenario `change` is present only for a tracked transition, so a
consumer can filter without re-deriving the counts. `added` counts scenarios
that are present now, absent from the baseline and not a new failure; an added
failing scenario is in `newFailures`. The `baseline.status` gives the previous
run's verdict; there is no baseline title or time, because the schema-2 summary
has neither.

## 6. Test, host and integration implications

### 6.1 Test matrix

| Layer | Must be pinned |
| --- | --- |
| Matcher (new unit) | Decision table above; pass/fail/undefined/ambiguous/skipped transitions; added and absent rows; duplicate names; outline rows with and without coordinates; renamed file keeps identity; renamed feature/scenario becomes removed+new; ambiguous group is excluded and counted; no order-based pairing |
| Baseline reader | Missing file; empty; invalid JSON; wrong `schemaVersion`; non-regular file; oversized file; hostile types/NaN/negative counts; prototype-shaped keys; control/bidi characters in names; only identity/status fields are trusted; no paths from the baseline reach the report as links or files |
| Summary/JSON | `baseline` block and per-scenario `change` only with a baseline; schema stays 2; key order stable; no absolute paths; no-flag JSON has no baseline keys (only the additive example coordinate on outline rows) and CI is byte-identical; no-flag HTML carries no baseline data (ideally byte-identical by reusing styles); a baseline that itself contains a `baseline` block is ignored safely |
| CLI | `--baseline` with `--out`, `--json`, `--ci`, `--pdf`; rejection with only `--email`; collision with an input, the logo, `--out`, `--history`, `--ci-out`, `--email`, `--pdf`; a baseline inside an input directory is rejected even when missing; the `--json > baseline.json` truncation trap is documented in `docs/CI.md` (the CLI cannot detect a shell truncation) |
| Report | Panel counts and links; row badges; escaping; no-JS; print/PDF; 320/390/768/1024/1440 px and 200 % text; German labels; no layout regression in the triage/source strip |
| CI | Markdown line exact text; complete counts; no line without a baseline; GitHub/Azure bytes unchanged; caps unaffected |
| E2E | Two real runs sharing one baseline; a renamed `*.feature` file; a fixed scenario, a new failure and a not-in-this-run scenario visible at 320 and 1440; print/PDF contains the panel |

The repo's ISTQB rules apply: equivalence classes for statuses, a decision table
for the transitions, boundary values for the file cap and zero/one/many
scenarios, and state transitions for absent → present → absent.

### 6.2 Host and gate

- This is a report-shell change: run the relevant host rows in
  `docs/DROP-IN-VALIDATION.md:25-33` after implementation, and the full required
  matrix before the 0.6.0 tag (`:180-191`; `AGENTS.md:121-123`).
- Add one live two-run baseline check, preferably Playwright movies-app
  (`5d2cdf0`) or the cucumber-js host: run once, keep `summary.json`, rename a
  spec/feature file in a temporary copy, run again with `--baseline`, record the
  new/fixed/not-in-this-run counts and the absence of absolute paths. Record the
  host, pin and result in `docs/DROP-IN-VALIDATION.md`.
- Browser gate: Chromium, Firefox and WebKit on Linux/macOS at 320, 390, 768,
  1024 and 1440 px plus 320 px at 200 % text (`AGENTS.md:110-116`); Windows
  `npm run check` stays green.
- No new runtime dependency. The reader uses Node built-ins, like the history
  reader.
- Performance: the matcher is O(n) over at most the existing input cap; the
  baseline projection should discard steps/messages and keep only identity,
  status and executed. The baseline file is never embedded in the HTML, so the
  report grows by the panel/badges only with the flag, plus any always-on
  CSS/catalog bytes. Measure the always-on growth even without the flag; the
  repo treats report size as a product requirement.
- Security: the baseline is untrusted JSON at a new trust boundary. Reuse the
  history reader's posture (regular file, size cap, strict schema, reject rather
  than coerce) and escape every name in every surface. SEC review is triggered;
  ILA for en/de; UXR for the panel; CMP because it is user-facing; STR for the
  new module seam; PCA if the diff touches the summary hot path.

## 7. Decisions only the user can make

**Q1. Baseline source and lifecycle.** Recommended: an explicit
`--baseline <summary.json>`, read-only, no automatic writer. A missing baseline
should exit 1, not start empty: an explicit comparison that silently does
nothing is a CI trap, and a first run simply omits the flag. The user (or CI)
keeps the previous `--json` output under a separate path. The alternative is an
auto-written per-run summary next to `--history`; it is more convenient but
stores scenario names and paths in a second artifact, contradicts the
aggregate-only, one-sidecar promise, would outgrow the 1 MiB cap if put in the
sidecar, and needs its own retention/atomicity design. A third option (scenario
hashes in the history sidecar) is rejected because it hides the names the report
must show and changes schema 1.

If the explicit file is chosen, the CI recipe must not do
`tolkira ... --json > summary.json --baseline summary.json`: the shell truncates
the file before Tolkira starts. Document a separate path and a copy/cache step.

**Q2. What "new" and "removed" mean in the release copy.** Recommended:
"new" means **newly failing** (including an added failing scenario), and
"removed" is written as **"not in this run"** because a deleted scenario, a
never-started scenario and a sharded-away scenario are indistinguishable in the
summary. The alternative is to headline **newly added scenarios** (presence, not
failure) and call the absent set "removed"; that is louder but less useful and
less honest. The user's answer fixes the panel labels, the CI sentence and the
JSON keys.

## 8. 0.6.0 story

Tolkira 0.6.0 answers the question a trend cannot: **what changed?** Point
`--baseline` at the previous run's `--json` summary, and the same report, JSON
summary and CI text separate new failures from fixed, still-failing and
not-in-this-run scenarios. Matching is name-based, so reordered runs and renamed
feature files keep their identity; outline examples are matched by their example
row, and anything ambiguous is stated rather than guessed. Without `--baseline`,
no baseline data appears, the CI bytes are unchanged, and the summary gains only
the additive example coordinate that makes the next comparison possible.
