# Parity research, 2026-11-24

**Scope.** Fresh, source-verified comparison of the Cucumber HTML reporters
and the two platform references, against Tolkira 0.6.0. No product code,
README, comparison page, spec or `package.json` was changed. This file is the
only new artifact and is left uncommitted.

**Method.** Versions and dates come from the npm registry, the GitHub API,
Maven Central metadata and the projects' own release pages. Feature claims come
from the primary docs and, where the docs are silent, from the current source
on the default branch. Downloads are npm installs in the 30 days ending
2026-11-23; they are an adoption proxy, not a user count. GitHub stars, fork
counts and the Jenkins installation share are also proxies. No vendor site used
here was unreachable. The only blocked endpoint was PyPI's download-stats API
(HTTP 401), so pytest-html has no download number.

**Bottom line.**

- No P0 blocker was found. Tolkira 0.6.0 covers the core content and navigation
  of all three Cucumber reporters. The remaining differences are either
  deliberate boundaries or platform features.
- The official formatter is now 24.4.0. Its 24.3/24.4 releases changed the
  Messages dependency and a Java OSGi header, not the report surface.
- `net.masterthought:cucumber-reporting` is at 5.12.1, not the 5.8.6 that the
  Maven Central search API still returns. It is actively maintained.
- The old reporter is unchanged at 7.2.0 and still has the largest npm install
  base among the Cucumber reporters after the official formatter. Its themes,
  charts and external screenshots remain the visible migration losses.
- Allure 3 has moved further into agent tooling. `allure agent`, skills and a
  Markdown output directory are now the strongest agent-discoverability
  reference, ahead of simple `llms.txt`.

### 2.3 Matrix notes

- **Official formatter retries.** The React acceptance fixture for the retry
  sample renders one row per test case and hides superseded attempts; it does
  not expose an attempt history. The formatter has had no CLI since 19.0.0.
  Sources: [retry spec](https://github.com/cucumber/react-components/blob/main/src/components/app/FilteredDocuments.spec.tsx),
  [CHANGELOG 19.0.0](https://github.com/cucumber/html-formatter/blob/main/CHANGELOG.md).
- **Old reporter search and filters.** Issue #147 asks for a failed-only
  default, a search box and a feature list; the Bootstrap template has no search
  or status-filter control. The reporter has a failed summary option, not a
  live filter. Sources: [issue #147](https://github.com/gkushang/cucumber-html-reporter/issues/147),
  [Bootstrap template](https://github.com/gkushang/cucumber-html-reporter/blob/develop/templates/bootstrap/index.html).
- **cucumber-reporting search.** Its pages have overview tables, feature pages,
  tag pages, a failures page and a trends page, but no search input or live
  status filter in the templates. The tag overview is navigation, not a filter.
  Sources: [README](https://github.com/damianszczepanik/cucumber-reporting#readme),
  [templates](https://github.com/damianszczepanik/cucumber-reporting/tree/master/src/main/resources/templates).
- **cucumber-reporting attachments.** Images, video, text and unknown files are
  rendered from the `embeddings/` directory, so the report is a folder, not one
  file. Source: [embeddings.vm](https://github.com/damianszczepanik/cucumber-reporting/blob/master/src/main/resources/templates/macros/json/embeddings.vm).
- **MCHR single file.** The README and 4.7.0 options still describe a report
  directory. The open request to embed all assets was closed with the
  maintainer comment "This feature is planned in upcoming release" on
  2026-06-03; no shipped single-file option was found in the 4.7.0 docs.
  Source: [issue #190](https://github.com/WasiqB/multiple-cucumber-html-reporter/issues/190).
- **MCHR retries.** The maintainer closed the retry request with "This reporter
  has no knowledge about the runs ... it only translates what it gets." The
  4.7.0 source has no attempt model. Source:
  [issue #221](https://github.com/WasiqB/multiple-cucumber-html-reporter/issues/221).
- **Allure single file and email.** The Awesome plugin supports
  `--single-file`; the default is a directory served by `allure open`. The
  `mail` plugin produces a ready-to-send HTML email but is not included in the
  `allure` package. Sources:
  [generate](https://allurereport.org/docs/v3/generate-report/),
  [view](https://allurereport.org/docs/v3/view-report/),
  [llms-full](https://allurereport.org/llms-full.txt).
- **Tolkira external attachments.** Deliberately rejected by ADR 0006; remote
  URLs are refused and attachments stay inline. Source:
  [ADR 0006](https://github.com/Silasoa/tolkira/blob/main/docs/adr/0006-inline-attachments.md).

## 3. What users rely on / love

### 3.1 Official Cucumber HTML formatter

The strongest reliance signal is distribution: the formatter is built into
cucumber-ruby, cucumber-jvm, cucumber-js and Reqnroll, and it has 17.1 million
npm installs in the last 30 days. Users do not choose it as a separate tool;
they get it from their Cucumber runner. Source:
[README](https://github.com/cucumber/html-formatter#readme),
[npm downloads](https://api.npmjs.org/downloads/point/last-month/@cucumber/html-formatter).

What they rely on:

- The Gherkin document as written: rules, backgrounds, outlines, examples and
  tags, with examples numbered `#1.1` and so on. Source:
  [Examples.tsx](https://github.com/cucumber/react-components/blob/main/src/components/gherkin/Examples.tsx).
- Hooks, including test-run hooks, and failed-hook evidence. Source:
  [TestRunHooks.tsx](https://github.com/cucumber/react-components/blob/main/src/components/app/TestRunHooks.tsx).
- Search over the Gherkin source, tag expressions and status checkboxes.
  Sources: [FeatureSearch.ts](https://github.com/cucumber/react-components/blob/main/src/search/FeatureSearch.ts),
  [ControlledSearchProvider.tsx](https://github.com/cucumber/react-components/blob/main/src/components/app/ControlledSearchProvider.tsx).
- Inline and external attachments, including images, video, logs, URI lists
  and JSON. Source:
  [Attachment.tsx](https://github.com/cucumber/react-components/blob/main/src/components/gherkin/attachment/Attachment.tsx).
- One file that opens without a server, at the cost of a React bundle.

What users praise and complain about:

- "The new html formatter is much easier to read and use for debugging of test
  failures" is followed in the same issue by "Our 423 scenarios produce an html
  report file of 314MB." The praise and the size complaint are one thread.
  Source: [issue #62](https://github.com/cucumber/html-formatter/issues/62).
- Metadata is still requested: [issue #106](https://github.com/cucumber/html-formatter/issues/106).
- Large attachments are still requested as external files:
  [issue #281](https://github.com/cucumber/html-formatter/issues/281).
- Per-scenario duration is still requested:
  [issue #375](https://github.com/cucumber/html-formatter/issues/375).
- Excluding unrun or unknown scenarios is still discussed:
  [issue #49](https://github.com/cucumber/html-formatter/issues/49),
  [issue #61](https://github.com/cucumber/html-formatter/issues/61).

UX patterns a report user has learned to expect: a header pass rate in the
form `x % (n / m)`, status checkboxes, a search box that accepts tag
expressions, a document accordion, numbered examples, a hooks disclosure and
attachment details. The formatter is a single-page React app: without
JavaScript the page is blank. Source:
[index.mustache](https://github.com/cucumber/html-formatter/blob/main/javascript/src/index.mustache).

### 3.2 cucumber-html-reporter 7.2.0

This is the tool most legacy-JSON teams still have in their pipeline. It has
2.37 million npm installs in the last 30 days despite a two-year gap with no
npm publish (2024-10-01 to 2026-11-25), no GitHub release since 6.0.0 in March
2023, and 91 open items. It resumed on 2026-11-25 with one merged bug fix and
the 7.2.1 patch.
Sources: [npm](https://www.npmjs.com/package/cucumber-html-reporter),
[repo](https://github.com/gkushang/cucumber-html-reporter),
[issue #296](https://github.com/gkushang/cucumber-html-reporter/issues/296).

What users rely on:

- One HTML file generated from the legacy JSON their runner already writes.
- Four themes (`bootstrap`, `hierarchy`, `foundation`, `simple`), a brand title,
  arbitrary metadata, inline screenshots and a failed-summary grid. Source:
  [README](https://github.com/gkushang/cucumber-html-reporter#readme).
- A visual summary with pie charts that stakeholders recognize.

What users say:

- "first of all, big thanks for only useful Cucumber JS HTML reporter!" opens a
  long UX complaint that asks for a failed-only default, a search box and a
  feature list. That is direct evidence of both loyalty and the missing
  navigation. Source:
  [issue #147](https://github.com/gkushang/cucumber-html-reporter/issues/147).
- "Thanks for the awesome cucumber html report. The report speaks for itself"
  appears in a Jenkins pie-chart bug. The praise is real, but the context is a
  broken chart, which is itself evidence of the CDN problem. Source:
  [issue #71](https://github.com/gkushang/cucumber-html-reporter/issues/71).
- The recurring pain is offline use and dependency rot: "Offline report"
  ([#167](https://github.com/gkushang/cucumber-html-reporter/issues/167)), a VPN
  blocking the Bootstrap CDN
  ([#259](https://github.com/gkushang/cucumber-html-reporter/issues/259)),
  Messages/Rule support
  ([#254](https://github.com/gkushang/cucumber-html-reporter/issues/254)) and
  old dependencies
  ([#303](https://github.com/gkushang/cucumber-html-reporter/issues/303)).

UX patterns users learned: choose a theme, read a metadata table, scan a pie
chart, open feature/scenario accordions, look at tags and use a failed-summary
grid. The Bootstrap template loads Bootstrap 3, jQuery 1.12, Moment 2.5 and
Google Charts from public CDNs. Source:
[Bootstrap template](https://github.com/gkushang/cucumber-html-reporter/blob/develop/templates/bootstrap/index.html).

### 3.3 net.masterthought cucumber-reporting 5.12.1

This is the Java/Jenkins incumbent. The README says it was "primarily created
to publish cucumber reports on the Jenkins build server" and that the generated
report "has no dependency so can be viewed offline." The Jenkins plugin page
reports installation on 3.64 % of controllers. Sources:
[README](https://github.com/damianszczepanik/cucumber-reporting#readme),
[Jenkins plugin](https://plugins.jenkins.io/cucumber-reports/).

What users rely on:

- Jenkins publishing with build status, classifications and historical reports.
  The plugin keeps a configurable number of builds and can fail a build on
  failed features, scenarios or steps. Source:
  [plugin docs](https://plugins.jenkins.io/cucumber-reports/).
- An overview page, per-feature pages, a failures page, tag overview and tag
  drill-down pages, and a trends page. Source:
  [README](https://github.com/damianszczepanik/cucumber-reporting#readme).
- Trends across builds through an opt-in JSON file (`setTrendsStatsFile`), with
  feature, scenario, step and duration charts. Source:
  [Configuration.java](https://github.com/damianszczepanik/cucumber-reporting/blob/master/src/main/java/net/masterthought/cucumber/Configuration.java),
  [overviewTrends.vm](https://github.com/damianszczepanik/cucumber-reporting/blob/master/src/main/resources/templates/generators/overviewTrends.vm).
- Classifications (platform, browser, branch, build), custom CSS and custom JS.
- Attachments in a sibling `embeddings/` directory, not inline.

What users say:

- The highest-reaction result in the checked open-issue search is "Release
  notes?" with 14 reactions: users are actively tracking releases, not just
  consuming the report. Source:
  [issue #901](https://github.com/damianszczepanik/cucumber-reporting/issues/901).
- A user running the generator in an EKS microservice with S3 input/output asks
  for in-memory generation because the current flow writes inputs, static
  resources, HTML and embeddings to a mounted volume. That is evidence of use
  outside Jenkins, and of the folder model's friction. Source:
  [issue #957](https://github.com/damianszczepanik/cucumber-reporting/issues/957).
- Other recurring themes in the top issues are sorting by duration, grouping
  identically named features, hook output, pending-as-failed and chart
  rendering.

UX patterns users learned: an overview table with charts, a feature list, a
tag overview, a failures page, a trends page, build/classification metadata and
expand/collapse controls. The report is a folder of pages, not a portable file.

### 3.4 multiple-cucumber-html-reporter 4.7.0

MCHR is the active dashboard alternative: 1.17 million npm installs, 287 stars,
4 open items and a release on 2026-11-22. Source:
[npm](https://www.npmjs.com/package/multiple-cucumber-html-reporter),
[repo](https://github.com/WasiqB/multiple-cucumber-html-reporter).

What users rely on:

- A dashboard with feature/scenario scoring, search, filter and sort.
- Metadata cards for browser, device, platform, app version and custom data.
- Multiple runs of the same feature consolidated in one report.
- Dark mode; English, Spanish, French, Portuguese and Arabic labels, with RTL
  for Arabic.
- A separate email-able report (`emailReport`), custom logo, colours, footer and
  CSS.
- A CLI (`mchr`) with an onboarding wizard, plus a programmatic `generate()`.
- Streaming generation for suites with large screenshot/video attachments, and
  an `externalizeMedia` option that writes media to `assets/media/`.

Sources: [README](https://github.com/WasiqB/multiple-cucumber-html-reporter#readme),
[docs](https://www.multiple-cucumber-html-reporter.com/docs),
[options](https://www.multiple-cucumber-html-reporter.com/docs/options),
[attachments](https://www.multiple-cucumber-html-reporter.com/docs/attachments).

What users say:

- "Hi, I love this report but the scenarios name don't show" is a 2017 issue;
  it is old but direct praise. Source:
  [issue #1](https://github.com/WasiqB/multiple-cucumber-html-reporter/issues/1).
- The single-file request has 4 reactions and a 2025 comment calling the
  folder "a bit unmanageable in CI, moreover with multiple parallel runs". The
  maintainer replied in 2026 that it is planned. Source:
  [issue #190](https://github.com/WasiqB/multiple-cucumber-html-reporter/issues/190).
- The retry request was closed with the explanation that the reporter only
  translates input and has no knowledge of runs. Source:
  [issue #221](https://github.com/WasiqB/multiple-cucumber-html-reporter/issues/221).
- The highest-reaction result in the checked issue search is an image-rendering
  regression in 3.9.0 with 7 reactions, a reminder that attachments are the
  fragile part of this model. Source:
  [issue #413](https://github.com/WasiqB/multiple-cucumber-html-reporter/issues/413).

UX patterns users learned: dashboard cards, a feature list and detail page,
metadata cards, chart panels, search/filter/sort, dark mode, a language choice
and an email report. It is a folder-first product; single-file output is still
not shipped.

### 3.5 Allure 3

Allure is the platform reference, not a Cucumber reporter. It has 2.59 million
npm installs, 30+ framework integrations, and active 3.33.0 development. Its
own `llms.txt` says Allure 2 is still the majority version, so the Allure 3
feature set is aspirational for many users. Sources:
[npm](https://www.npmjs.com/package/allure),
[llms.txt](https://allurereport.org/llms.txt).

What users rely on:

- History and retries: a JSONL `historyPath`, per-test history, retries, and
  "new / fixed / regressed / malfunctioned" transitions. Source:
  [history and retries](https://allurereport.org/docs/history-and-retries/).
- Search and filtering by name, tags, status, severity, categories and
  environments. Source:
  [sorting and filtering](https://allurereport.org/docs/sorting-and-filtering/).
- Steps, attachments, categories, environments, quality gates, timeline,
  performance metrics, CSV and metrics export.
- A default directory/site served by `allure open`, or a single file through
  the Awesome plugin. Source:
  [view report](https://allurereport.org/docs/v3/view-report/).
- Agent Mode: `allure agent` wraps the test command, writes an `agent-output/`
  directory with `index.md`, manifest, tests, logs and `awesome/`, and supports
  `allure agent inspect` on existing results. It also ships skills and a
  capabilities command. Source:
  [Agent Mode](https://allurereport.org/docs/agent-mode/).

UX patterns users learned: an overview dashboard, suites/behaviors/packages
navigation, categories, history and retry tabs, attachment viewers, quality
gates and a timeline. The cost is a heavier site and a local server
recommended for the default view.

### 3.6 UX references: Playwright and pytest-html

These are not Cucumber rows; they set expectations.

**Playwright HTML reporter.** It produces a self-contained folder served as a
web page, with `onlyFailures`, retries, `attachmentsBaseURL`,
`doNotInlineAssets`, `mergeFiles`, sharding through blob reports, a trace
viewer and a `github` annotation reporter. It also has JSON and JUnit
reporters. Source: [Playwright reporters](https://playwright.dev/docs/test-reporters).
The learned patterns are failure-only views, retries with evidence, a
self-contained artifact that can be zipped, and CI annotations as a first-class
output.

**pytest-html 4.2.0.** It writes HTML plus separate assets by default for CSP
reasons and offers `--self-contained-html` for one file; images added as files
or links may still be external. It has an environment table through
`pytest-metadata`, extras (HTML, JSON, text, URL, image), collapsed passed rows,
and `visible`, `sort` and `collapsed` query parameters. It has no free-text
search. Source: [user guide](https://pytest-html.readthedocs.io/en/latest/user_guide.html).
The learned patterns are an environment block, collapsible result rows,
query-string display state, and a single-file switch that is explicit about its
limits.

### 3.7 Patterns a report user expects

Across the established tools, the repeated expectations are:

1. A summary header with counts, pass rate and duration.
2. A failed-first or failure-only view; passing rows may be collapsed.
3. Search plus status and tag filters, with shareable URL state when possible.
4. Gherkin structure: rules, backgrounds, outlines, examples and tags.
5. Step-level errors, hooks and attachments, with screenshots visible.
6. Environment and CI metadata: browser, OS, build, commit, branch, job link.
7. Retry-aware rows: final status visible, attempts explainable.
8. A portable artifact: one file or a folder that opens offline.
9. A machine-readable output for CI, even if it is only JUnit or JSON.
10. Print/PDF or an email summary for stakeholders.
11. Responsive layout and readable long text; accessibility is improving but
    rarely formally audited.
12. Agent-readable docs or output; Allure is the first to make this a named
    product surface.

Sources: the tool sections above; the cross-tool synthesis is also consistent
with Tolkira's own issue review in
[`reporting-feature-requests.md`](reporting-feature-requests.md).

## 4. Gap list against Tolkira 0.6.0

### 4.1 How P0 was judged

A P0 is a case where a user cannot complete a core Cucumber-report job that one
of the three Cucumber reporters supports, or where migration loses report
content. A P1 is a valuable improvement with clear evidence but no blocked
job. A P2 is a deliberate non-goal, a different product shape, or work that
conflicts with the one-file/offline baseline.

### 4.2 Cucumber-reporter parity

**P0 — none found.** The evidence does not support a blocking gap:

- The official formatter's content surface is Messages, Gherkin structure,
  hooks, embedded attachments, search and status/tag filtering. Tolkira 0.6.0
  covers those for Messages, including rules, backgrounds, outlines, examples,
  hook names, test-run hooks, undefined/ambiguous diagnostics and Markdown
  descriptions. Sources:
  [PRODUCT](https://github.com/Silasoa/tolkira/blob/main/docs/PRODUCT.md),
  [LIMITATIONS](https://github.com/Silasoa/tolkira/blob/main/docs/LIMITATIONS.md).
- The official formatter has no JSON summary, CLI, history or baseline; Tolkira
  adds those. Source:
  [CHANGELOG](https://github.com/cucumber/html-formatter/blob/main/CHANGELOG.md).
- The old reporter's unique options are visual or external: four themes, pie
  charts, column layout and external screenshot folders. None is required to
  read a run, and the product has an explicit non-goal for theme parity.
  Source:
  [COMPATIBILITY](https://github.com/Silasoa/tolkira/blob/main/docs/COMPATIBILITY.md).
- MCHR is a folder/dashboard product with multi-run grouping, five UI languages
  and an email report. Tolkira has the email summary and en/de; the folder and
  dashboard are a different delivery model, not a content gap. Source:
  [MCHR README](https://github.com/WasiqB/multiple-cucumber-html-reporter#readme).

The candidates that look like P0 at first pass are reviewed in 4.4.

**P1 — Cucumber parity improvements worth considering.**

1. **Tag overview with counts.** cucumber-reporting has a tag overview and tag
   drill-down; the old reporter exposes tags but no summary; MCHR has tag
   filtering. Tolkira has a tag dropdown, tag-expression search and a
   feature-by-status matrix in Details, but no tag summary with pass/fail
   counts. Recommendation: add a small tag table (tag, scenarios, failed,
   skipped) beside the existing tag filter, using model tags and no schema
   change. Evidence:
   [cucumber-reporting README](https://github.com/damianszczepanik/cucumber-reporting#readme),
   [MCHR README](https://github.com/WasiqB/multiple-cucumber-html-reporter#readme),
   [PRODUCT](https://github.com/Silasoa/tolkira/blob/main/docs/PRODUCT.md).

2. **Absolute scenario start time.** The old reporter's `scenarioTimestamp`
   option shows the start timestamp of each scenario; Tolkira shows relative
   time and per-scenario duration. Recommendation: show an absolute start time
   in the scenario detail, keeping relative time for scanning; no new file or
   schema. Evidence:
   [old reporter README](https://github.com/gkushang/cucumber-html-reporter#readme),
   [COMPARISON](https://github.com/Silasoa/tolkira/blob/main/docs/COMPARISON.md).

3. **Earlier Cucumber attempts.** Tolkira already shows a collapsed
   "Earlier attempts" block for Playwright retries. The official formatter shows
   only the final attempt; Allure shows retries and history. Recommendation:
   extend the existing block to Messages `testCaseStarted` attempts when the
   stream carries them; keep it report-only, capped and out of counts, as the
   Playwright block already is. Evidence:
   [Allure retries](https://allurereport.org/docs/history-and-retries/),
   [Tolkira LIMITATIONS](https://github.com/Silasoa/tolkira/blob/main/docs/LIMITATIONS.md).

**P2 — deliberate non-goals.**

- **Themes, charts and column layouts.** The old reporter ships four themes and
  pie charts; Tolkira has one shell with branding and dark mode. This is a
  product non-goal, not a missing report fact. The repeated user requests are
  about summary, print and branding, which Tolkira already answers. Source:
  [old reporter README](https://github.com/gkushang/cucumber-html-reporter#readme),
  [reporting feature requests](reporting-feature-requests.md).
- **External attachments and split assets.** The official formatter accepts
  `attachment.url`; the old reporter has `storeScreenshots`; MCHR has
  `externalizeMedia`; cucumber-reporting writes an `embeddings/` folder.
  Tolkira rejects remote URLs and keeps one file by ADR 0006. Revisit only when
  a user cannot share a report because of media size, and only with a new ADR.
  Sources: [issue #281](https://github.com/cucumber/html-formatter/issues/281),
  [ADR 0006](https://github.com/Silasoa/tolkira/blob/main/docs/adr/0006-inline-attachments.md).
- **Legacy outline reconstruction and legacy Rule structure.** Legacy JSON
  arrives with examples expanded and does not carry the rule tree; the old
  reporter also flattens examples. Tolkira groups Messages outlines and shows
  Rules there. Recommendation: document the legacy limitation rather than
  invent structure the format does not carry. Source:
  [LIMITATIONS](https://github.com/Silasoa/tolkira/blob/main/docs/LIMITATIONS.md).
- **Custom JavaScript, CDN mode and browser launch.** The official Java/.NET
  wrappers allow custom JS; the old reporter can launch a browser. Both
  conflict with the CSP, one-file, no-network baseline. Keep rejecting them.
  Source: [official README](https://github.com/cucumber/html-formatter#readme),
  [COMPATIBILITY](https://github.com/Silasoa/tolkira/blob/main/docs/COMPATIBILITY.md).
- **A native Jenkins plugin.** cucumber-reporting's Jenkins plugin is installed
  on 3.64 % of controllers. Tolkira documents Jenkins HTML Publisher and
  `--static`; a plugin is ecosystem work with a different support burden.
  Recommendation: keep the recipe, not a plugin. Source:
  [Jenkins plugin](https://plugins.jenkins.io/cucumber-reports/).
- **`reportSuiteAsScenarios`, `failedSummaryReport`, `columnLayout`.** The
  compatibility shim warns and ignores these. Tolkira shows feature and
  scenario counts, a failed-first view and a responsive one-column shell, so
  the user-visible outcome is covered even though the option names are not.
  Source: [COMPATIBILITY](https://github.com/Silasoa/tolkira/blob/main/docs/COMPATIBILITY.md).

### 4.3 Platform parity (Allure 3 / ReportPortal)

Allure is the reference for history, retries, categories, quality gates and
agent output. ReportPortal is the server-based end of the same spectrum. The
question is not whether Tolkira can match them; it cannot without becoming a
platform. The question is which platform surfaces are worth a small, file-local
subset.

**P0 — none.** A single-file Cucumber report does not need a server, a database
or a run store to answer the five product questions in `PRODUCT.md`.

**P1 — platform-adjacent improvements worth considering.**

1. **Agent Markdown output and an artifact manifest.** Allure Agent Mode
   writes `agent-output/index.md`, a manifest, per-test summaries, logs and the
   generated report path; the agent reads that before source code. Tolkira
   already writes a JSON summary, but an agent still has to know which of
   `report.html`, `summary.json`, `email.html`, `report.pdf`, `history.json` and
   a baseline exists. Recommendation: add an opt-in `--agent-md <file>` (or
   `index.md`) derived from the existing summary, plus a small manifest of
   generated artifacts; no second data model. Evidence:
   [Allure Agent Mode](https://allurereport.org/docs/agent-mode/).
2. **A capabilities query.** Allure exposes `allure agent capabilities --json`
   so an agent can discover options without scraping help text. Recommendation:
   add `tolkira capabilities --json` with version, inputs, outputs, limits,
   schema version and exit-code semantics. Evidence:
   [Allure Agent Mode](https://allurereport.org/docs/agent-mode/).
3. **A small agent skill or `AGENTS.md` snippet.** Allure ships skills through
   `npx skills add allure-framework/skills` and configures a project guide plus
   a root agent entry file. Recommendation: ship one skill or a copy-paste
   `AGENTS.md` block that runs `--json`, checks `executed`, attaches the report
   and reads warnings; link it from `llms.txt`. Evidence:
   [Allure Agent Mode](https://allurereport.org/docs/agent-mode/).

**P2 — platform features Tolkira should not chase.**

- **Scenario-level history and a run store.** Allure links each test across
  runs and computes stability; Tolkira's history sidecar is aggregate-only and
  deliberately excludes scenario names, paths, tags and attachment content.
  Adding per-test history would grow the sidecar and weaken the privacy
  baseline. Revisit only if users ask for flaky trends and accept the larger
  artifact. Sources:
  [Allure history](https://allurereport.org/docs/history-and-retries/),
  [Tolkira history limits](https://github.com/Silasoa/tolkira/blob/main/docs/LIMITATIONS.md).
- **Quality gates, categories, timeline, performance metrics, CSV/metrics
  export.** These are Allure platform surfaces; a file report can show counts
  and durations but should not become a gate engine. Source:
  [Allure features](https://allurereport.org/docs/features-overview/).
- **A server, RBAC, test management, ML triage, trace viewer.** ReportPortal
  and Allure TestOps territory; outside the product's non-goals. Source:
  [ReportPortal](https://github.com/reportportal/reportportal),
  [PRODUCT non-goals](https://github.com/Silasoa/tolkira/blob/main/docs/PRODUCT.md).
- **More locales and RTL.** MCHR supports five languages including Arabic RTL;
  Tolkira ships en/de and no RTL layout. The current contract is explicit;
  expanding it is content and layout work, not a parity bug. Source:
  [MCHR README](https://github.com/WasiqB/multiple-cucumber-html-reporter#readme),
  [Tolkira I18N limits](https://github.com/Silasoa/tolkira/blob/main/docs/LIMITATIONS.md).

### 5.1 What Tolkira could add beyond `llms.txt` and the JSON summary

1. **`tolkira capabilities --json` (P1).** Allure already exposes
   `allure agent capabilities --json`; an agent can discover the installed
   version, supported options and limits without parsing `--help`. For Tolkira
   this is a small, stable object: version, inputs, outputs, limits, schema
   version and exit codes. Evidence:
   [Allure Agent Mode](https://allurereport.org/docs/agent-mode/).

2. **An agent-facing `index.md` plus artifact manifest (P1).** Allure Agent
   Mode's `agent-output/` is a review surface: `index.md` is the entry point and
   a manifest lists the run artifacts. Tolkira writes several optional outputs;
   an agent currently has to infer which exist from the command line. A small
   Markdown file with status, counts, first failures, warnings and paths would
   reduce token cost and wrong-path errors. Evidence:
   [Allure Agent Mode](https://allurereport.org/docs/agent-mode/).

3. **One agent skill or `AGENTS.md` snippet (P1).** Allure ships skills and
   configures a project guide plus a root agent entry file. Tolkira's
   `llms.txt` rules are close, but a skill can run the command, read
   `scenarios[].executed`, attach `report.html` and stop on warnings. Evidence:
   [Allure Agent Mode](https://allurereport.org/docs/agent-mode/).

4. **`llms-full.txt` (P2).** Allure publishes both a short index and a full-text
   corpus. Tolkira's `llms.txt` is a short map; a full-text variant would help
   agents answer limit questions without fetching multiple docs. Evidence:
   [Allure llms.txt](https://allurereport.org/llms.txt),
   [llms-full.txt](https://allurereport.org/llms-full.txt).

5. **Do not duplicate `--ci markdown` (already shipped).** A new "agent
   summary" text format would overlap the existing Markdown CI output. If the
   manifest in item 2 is added, keep it a path/status index, not a second
   human report. Source:
   [Tolkira CI](https://github.com/Silasoa/tolkira/blob/main/docs/CI.md).

## 6. Open questions and what could not be verified

- **MCHR single-file status.** The maintainer said in June 2026 that it is
  planned; the issue is closed and 4.7.0 docs still describe a folder. I did not
  find a hidden option, but I did not run 4.7.0 against a real project.
- **MCHR retry grouping.** The source has no attempt model and the maintainer
  says the reporter only translates input. I did not run a rerun-producing
  Cypress/Cucumber project against 4.7.0.
- **Official formatter retry display.** The React acceptance fixture and the
  prior 24.2.0 inspection indicate final-attempt-only, but I did not render a
  retry fixture with 24.4.0 in this pass.
- **cucumber-reporting download counts.** Maven Central does not publish them.
  The Jenkins 3.64 % installation share is a proxy, not a user count.
- **pytest-html download counts.** PyPI's stats API returned HTTP 401 without a
  key; no download number is claimed.
- **Allure 2 vs 3 adoption.** `llms.txt` says Allure 2 is still the majority,
  but gives no split. The npm `allure` count is the CLI, not report views.
- **Allure `reportLanguage` list.** The docs show the option and default `en`;
  the fetched page did not enumerate every supported language, so the matrix
  says "Partial" rather than naming a set.
- **ReportPortal feature audit.** I checked release, license, stars and
  repository only. I did not audit RBAC, ML triage or storage architecture.
- **MCHR trends.** The README promises multi-run consolidation and trend
  analysis; I did not verify whether it persists history across separate
  invocations or only renders runs supplied together. The matrix says
  "Partial — multi-run dashboard", not "history file".
- **Old reporter #71 quote.** The quote is genuine praise, but the issue is a
  Jenkins pie-chart failure; do not cite it as evidence that the charts work.
- **Jenkins plugin version.** The page reports 5.12.0 while Maven Central has
  5.12.1; the plugin release lags. Do not quote the plugin version as the
  library version.
- **No vendor site unreachable.** All primary docs, registries and repositories
  used here responded. The only blocked endpoint was PyPI's download-stats API.
