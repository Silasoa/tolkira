# Tolkira 0.6.0 audit — 2026-11-24

## What this repo does

Tolkira turns Cucumber legacy JSON, Cucumber Messages, JUnit XML and
Playwright JSON into one self-contained offline HTML report. Optional
outputs are a stable JSON summary, CI text, an HTML email body, a PDF, a
history sidecar and a baseline comparison.

## Scope and load assumed

The audit covered the CLI and the programmatic API, one run at a time, at
the load the docs claim: up to about 10k scenarios, a 100 MB total input,
50 MB per attachment, a 365-run history sidecar and a 10 MiB baseline.
The code was read from `src/`; the existing `dist/` build was used only
for throwaway probes because a benchmark holds `dist/` during this audit.

## What was run

- `npx vitest run test/inputs.test.ts test/summary.test.ts
  test/model-summary-cross-check.test.ts test/history.test.ts
  test/history-window.test.ts`: 5 files, 179 passed, 1 skipped.
- `npx vitest run test/playwright.test.ts
  test/playwright-retry-evidence.test.ts test/cli-history-window.test.ts
  test/cli-edge.test.ts`: 4 files, 107 passed, 3 skipped.
- Throwaway `dist` probes for findings 1-12: a `../.env` attachment
  leak, skipped/duplicate input accounting, an empty `.ndjson` scan, an
  orphan `testStepId` attachment, a malformed history target, a

### 1. P1 — Path attachments can read any file under the working directory

**What this is:** Playwright path attachments are read from two roots: the
input file's folder and the process working directory.

**Problem:** The working directory is normally the whole project. A report
JSON in `reports/` can name `../.env`, a CI token file or a private key;
the adapter reads the regular file and embeds it in the shareable HTML.
`SECURITY.md` says Tolkira processes untrusted test output, so this is a
data-exposure boundary, not just a convenience. The cwd root is
documented for the `reports/results.json` plus `test-results/` layout, so
the fix is a decision: make the cwd root opt-in, or keep it and accept
that a crafted report can read every project file. The current docs do
not state that consequence.

**Evidence:** `src/input/playwright.ts:1568-1575` adds
`process.cwd()` to the allowed roots; `939-941` resolves a relative path
against the input folder, then cwd; `884-890` opens the file after
`realpath` and the root check. `SECURITY.md:21-27` claims path handling
for untrusted output; `docs/PLAYWRIGHT-JSON.md:132-134,152-155` documents
the cwd root.

**Repro:** Put `run.json` in `reports/` and a `.env` with a token in the
project root. Set an attachment
`{name:"leak.txt", contentType:"text/plain", path:"../.env"}`. The token
appears in the generated HTML.

**Missing test:** A path outside the input folder but inside cwd should
be skipped by default, or require an explicit opt-in. Current tests cover
only paths outside both roots and symlinks.

### 2. P1 — Input accounting counts skipped files and checks the cap first

**What this is:** `loadResolvedInputs` reads every `.json`, `.jsonl`,
`.ndjson` and `.xml` file in a directory, then decides whether the file
is a report.

**Problem:** A `skip` decision still pushes an empty loader group. As a
result, `inputFiles`, `inputBytes`, the Details input row and the
post-render size warning include unrelated files such as `package.json`
or `tsconfig.json`. The 100 MB check also runs before the content hash:
two identical 51 MiB reports fail with `Inputs exceed 100 MB` even
though one copy would be deduplicated and each file is under the cap. A
large unrelated JSON can block the run for the same reason. The cap
error then tells the user to "use external attachments", which is a
non-goal, instead of offering a supported remedy.

**Evidence:** `src/input/load.ts:152` calls `addInputBytes` before the
read and hash at `155-165`; the `skip` branch is `216-217`; the group is
pushed at `220-225`. `src/run.ts:82-83` returns the counts. The error
text is `src/input/load.ts:14-21`.

**Repro:** A directory with `screenshot.ndjson`, `package.json` and
`tsconfig.json` returns `inputFiles: 3` and `inputBytes: 16393` instead
of one file and 16341 bytes. Two identical 51 MiB legacy arrays exit 1
with the cap error.

**Missing test:** Assert that `inputFiles` and `inputBytes` ignore
skipped files; that duplicate content is removed before the cap check;
and that the cap error names a supported remedy.

### 3. P2 — `writeHistory` overwrites a malformed history target

**What this is:** Before writing, `writeHistory` peeks at the existing
sidecar to preserve schema version 2.

**Problem:** The peek only checks that the target is a JSON object with a
supported `schemaVersion`. It does not apply the reader's run validation.
A target such as `{"schemaVersion":1,"runs":"not-an-array"}`, or a target
with one bad run entry, is valid enough for the writer and is replaced
with a new file. That loses the prior content and contradicts the
documented promise that a malformed target is rejected. The CLI is
protected because it calls `readHistory` first; the public `writeHistory`
API is not.

**Evidence:** `src/history.ts:390-418` validates only JSON, the object
and the schema version. `src/history.ts:439` uses that result before the
overwrite. `docs/AGENT-INTERFACE.md:499-501` says a malformed target is
rejected.

**Repro:** Write `{"schemaVersion":1,"runs":"not-an-array"}`, call
`writeHistory(file, [validRun])`; the call succeeds and the file is
replaced.

**Missing test:** A target with schema 1 and malformed `runs`, or one
bad entry, must reject and stay byte-identical. Existing tests cover
invalid JSON, an oversized target and an unsupported schema, but not a
malformed supported-schema target.

### 4. P2 — An empty `.jsonl`/`.ndjson` shard aborts a directory scan

**What this is:** A directory scan collects every supported file and
parses each one before rendering.

**Problem:** An empty Messages file in a directory is routed to
`messages-validation` and then `parseMessages`, which throws
`Input is empty`. One empty shard artifact therefore hides every valid
report beside it. JUnit already has the matching exception: a zero-test
document in a directory scan is skipped, while an explicitly named one
still fails. The Messages path has no equivalent, so a filtered or
zero-test shard cannot be tolerated in a scan.

**Evidence:** `src/input/detect.ts:110-111` routes an empty non-explicit
messages file to validation; `src/input/messages.ts:233-235` throws;
`src/input/load.ts:199-202` calls it. The JUnit skip is
`src/input/junit.ts:401-411`.

**Repro:** A directory with the `screenshot.ndjson` fixture and an empty
`shard.ndjson` exits 1 with `Input is empty` and writes no report. The
same empty file named explicitly should still exit 1.

**Missing test:** A directory scan with an empty `.ndjson` or `.jsonl`
plus a valid report should skip the empty file with a warning, or the
behavior should be documented as strict. An explicit empty file must
keep failing.

### 5. P2 — HTML and JSON disagree on some attachment counts

**What this is:** The JSON summary counts attachments per selected
test-case start; the report model only renders attachments whose test
step has a result.

**Problem:** If an attachment names a `testStepId` that is absent from
the selected test case, or whose step produced no `testStepFinished`,
the summary counts it but the HTML shows no attachment and Details
reports a lower total. A truncated Messages stream can produce exactly
that state: the attachment is emitted, then the process stops before the
step result. An attachment owned by a run hook whose start envelope is
missing has the same split. The docs say to open the HTML to see the
attachment; here there is nothing to see.

**Evidence:** `src/report/model.ts:596-598` collects the start's
attachments, but `609-611` skips a test step without a result and
`617-619` only attaches files to rendered steps. `src/summary.ts:329-332`
counts every attachment for the start; `382-385` decides the total.

**Repro:** Take `screenshot.ndjson` and change the attachment's
`testStepId` to `orphan-step`. `summarizeReport` returns
`attachments.total: 1` and `scenarios[0].attachments: 1`; the report
Details row says 0 and the image is absent.

**Missing test:** A model/summary cross-check with an attachment whose
step has no result, and one owned by a missing run-hook start, must agree
on the count and on whether the HTML shows it.

### 6. P2 — Playwright reports without timing fields pick the first attempt

**What this is:** The Playwright adapter chooses the final result by the
largest `retry` value and builds each attempt's timestamp from
`startTime`.

**Problem:** Both fields are optional in the adapter's validation. If
they are missing, every result gets `retry: 0` and the run timestamp, and
the reduce keeps the first result as final. A report with a failed first
result and a passed second result is then rendered as failed. The same
missing `startTime` also makes an otherwise empty report claim
`1970-01-01 00:00 UTC`, because the run timestamp falls back to zero.
Official Playwright reports normally carry both fields, but the adapter
accepts files without them and silently produces a wrong result or date.

**Evidence:** `src/input/playwright.ts:1234-1243` uses a strict `>`
comparison and defaults missing `retry` to 0; `522-526` and `1561-1563`
fall back to the run timestamp or zero. `src/report/model.ts:482-489`
turns that zero into a 1970 start date.

**Repro:** A report with two results, the first failed and the second
passed, and no `retry` or `startTime` fields returns a failed scenario.
An empty report with no `stats.startTime` renders the 1970 date.

**Missing test:** A retried report with omitted `retry` and `startTime`
must render the last executed result; a report with no usable start time
must omit the date rather than print 1970.

### 7. P2 — Playwright `expectedStatus: skipped` hides a failure

**What this is:** The adapter derives `skipped` from the test status,
the expected status or the final result status, and that flag wins over
the final result.

**Problem:** If a test is marked skipped but its final result is failed,
or unexpectedly passes, `skipped` is still true and the whole scenario is
rendered as skipped with every step skipped. A framework or a merged
report can produce that shape; the failure disappears from the report,
summary, CI and history. The `test.status === 'unexpected'` case should
be checked before the expected-skip flag.

**Evidence:** `src/input/playwright.ts:1245-1265` computes `skipped`
without excluding a failed or passed final result, then chooses `mode`.
`767-780` maps every step to `SKIPPED` in that mode.

**Repro:** A test with `expectedStatus: "skipped"`, `status:
"unexpected"` and one failed result becomes `status: "skipped"` in the
summary with skipped steps.

**Missing test:** Expected-skip plus a failed result must be failed;
expected-skip plus an unexpected pass must be a failed unexpected pass.

### 8. P2 — A Playwright spec without `file` loses the suite file name

**What this is:** A spec may inherit its file from the containing suite.
The feature key uses that inherited file, but the scenario and rule names
are built from `spec.file` alone.

**Problem:** When a spec has no `file`, the scenario URI falls back to
`playwright.spec.ts` and the rule name uses the same fallback, while the
feature name is the real file. The report and JSON summary then disagree
about where the scenario came from, and search/copy text shows a
fictional file. The inheritance code exists for suites; this one path
does not use it.

**Evidence:** `src/input/playwright.ts:1228` passes `spec.file` to
`fileUri`; `585-587` supplies the fallback. `1392-1396` correctly
computes the inherited `specFile` for `featureFor`.

**Repro:** A suite with `file: "a.spec.ts"` and a spec without `file`
returns a scenario at `playwright.spec.ts` and feature `a.spec.ts`.

**Missing test:** A suite-level file must appear in the scenario URI,
rule name and source label when the spec omits `file`.

### 9. P2 — An unvalidated Messages `attempt` can be `null` in JSON

**What this is:** `testCaseStarted` validation checks the id, test case
and timestamp, but not `attempt`.

**Problem:** A numeric value that JSON parses as `Infinity`, such as
`1e309`, reaches the summary unchanged. `JSON.stringify` then writes
`"attempt": null`, breaking the documented number field for agents. The
HTML model uses `Number.isFinite` and shows attempt 1, so the two
surfaces also disagree. A string attempt would leak as a string in JSON
while the model treats it as zero. The field should be a non-negative
safe integer or be rejected.

**Evidence:** `src/input/messages.ts:149-153` omits `attempt` from the
validator; `src/summary.ts:348` copies it; `src/report/model.ts:767`
handles non-finite values differently.

**Repro:** Replace the first `"attempt":0` in a Messages fixture with
`"attempt":1e309`; `--json` contains `"attempt": null` for that scenario.

**Missing test:** Attempt `1e309`, a string and a negative number must
either be rejected with a clear line error or normalised consistently;
the JSON summary must never contain `null` for `attempt`.

### 10. P2 — CI output does not cap scenario names, URIs or titles

**What this is:** GitHub and Markdown CI formats cap the message part of
an annotation and the failed-message snippet, but not the identity used
as a title or heading.

**Problem:** GitHub error titles use the full `feature: name` string, and
Markdown headings and code spans use full feature names, scenario names,
URIs and the `--title` heading. A long but valid test name becomes a
multi-megabyte workflow-command line or step-summary line. Provider
limits then truncate or reject the output, and the existing
`[truncated]` behavior is bypassed. The email renderer already caps names
at 200 characters; CI should apply the same cap.

**Evidence:** `src/ci.ts:160-163` does not truncate the GitHub title;
`354-369` and `421` do not truncate Markdown feature, name or URI text.
Only `failureMessage` uses `truncate` or `codeSpan` caps.

**Repro:** A Messages fixture with a 100k-character scenario name and
`--ci markdown` writes a 100k-character line (100,464 bytes of stdout on
this host).

**Missing test:** A long feature/name/URI/title must be capped in both
GitHub and Markdown output with an explicit marker, while the complete
counts stay intact.

### 11. P2 — Report write errors expose the random temporary path

**What this is:** `--out` and `--ci-out` write through `writeAtomic`,
but the CLI does not wrap their failures.

**Problem:** A failed report write prints the raw Node error. On a
directory target the message names the random `.<name>.<uuid>.tmp` file
and the target, not a clean `Cannot write report to <path>` line. The
email, PDF and history writers already hide the temporary file; the
report and CI-text paths do not. This is a confusing failure and leaks a
local temporary path into logs.

**Evidence:** `src/cli.ts:694-696` writes the report and `736-738` the
CI text with no wrapper; `756-759` prints the raw error. Compare the
wrapped writers at `213-256` and `457-465`.

**Repro:** Point `--out` at an existing directory. The stderr line starts
`tolkira: EPERM: ... rename '...outdir.<uuid>.tmp' -> '...outdir'`.

**Missing test:** A directory target for `--out` and `--ci-out` must
name the requested target and must not contain `.tmp` or a UUID.

### 12. P2 — `ignoreBadJsonFile` still fails on a non-feature JSON array

**What this is:** The compat `jsonDir` scan pre-validates `.json` files
before passing them to the core loader.

**Problem:** The pre-check only requires `Array.isArray(parsed)`. A
`numbers.json` containing `[1,2,3]` passes the pre-check, then
`planSidecar` rejects it as "not a legacy feature array", even with
`ignoreBadJsonFile: true`. The core loader would skip the same file, so
the drop-in adapter is stricter than the core and the option does not do
what its name says. An array of non-feature objects is accepted into the
merged sidecar instead of being skipped.

**Evidence:** `src/compat/options.ts:178-187` accepts any array;
`src/compat/cucumber-html-reporter.ts:42-57` requires every element to be
a feature object; `86-103` then throws in `planSidecar`.

**Repro:** A `jsonDir` with `happy.json` and `numbers.json` plus
`ignoreBadJsonFile: true` rejects with
`compat: ...numbers.json is not a legacy feature array`.

**Missing test:** The compat scan must use the same feature-shape
predicate as `detectInput`; `[1,2,3]` and an array of non-feature objects
must be skipped with a warning when `ignoreBadJsonFile` is true.

## Checked with no finding

- HTML text escaping was traced through report, Details, triage, matrix,
  trends, baseline, email, CI, attachments and error paths. No unescaped
  dynamic string reached markup.
- The Markdown allowlist blocks `javascript:`, `data:`, `file:` and
  relative links; images render as alt text only; raw HTML is escaped.
  `test/render-markdown.test.ts` covers the hostile cases.
- CSP hashes, the static `script-src 'none'` form, inline JSON escaping,
  metadata URL allowlisting and accent validation were checked; no
  injection path was found.
- The baseline reader's caps, regular-file checks, depth limit, prototype
  rejection and read-only behavior hold. The O(n²) history prune is
  accepted and not re-reported.
- The history BOM gap is already in the 0.6.1 draft and is not repeated.
- The three `<main>` elements are B-048 and are not repeated.
- External attachments as a feature remain a non-goal; only the error
  text that suggests them is reported.

## What I could not verify

- The browser matrix, print layout and the real Chromium PDF engine were
  not run; `npm run build` and `npm run check` were not run because a
  benchmark held `dist/`.
- No real 50 MB attachment, 10k-scenario browser session or multi-host
  run was measured. The stress numbers in the docs were not re-run.
- GitHub and Azure provider limits were not tested (no network). The
  CI finding is based on the generated line size, not a provider
  response.
- Generated catalogs and generated CSS were skimmed; every catalog string
  was not re-read. Some test files were sampled rather than read line by
  line; the targeted suites listed above pass.

## Verdict

No P0 was found. Fix finding 1 and finding 2 first; then 3 to 5. The
remaining items are sharp edges in accepted input shapes. The Markdown,
HTML-escaping and attachment-type allowlists look sound.
