# Limitations

Last verified: **2026-11-23**. "Verified" means the repository state on that
date: the cited fixture or test exists and passes. It does not mean every
producer was re-run on that date.

| Area | Status | Last verified | What it means |
| --- | --- | --- | --- |
| Behave 1.3.3 | Partial | 2026-11-19 | Real runs (`behave-real.json`, `behave-real-attachments.json`) cover pass/fail/error statuses, seconds-based durations, a multiline doc string, a data table, a multiline error message and an inline PNG. The recorded rich run contains one `error` status; `hook_error` and `cleanup_error` are covered by synthetic tests. Behave's formatter omits error text for `error` and `hook_error` step results; `cleanup_error` is recorded on the scenario/feature during context cleanup and is accepted defensively in a step result. Dry-run/WIP statuses (`untested`, `untested_pending`, `untested_undefined`, `pending_warn`) and `xfailed`/`xpassed` are unsupported, and scenario-level hook failures without a step result are not reconstructed. |
| JUnit XML | Basic | 2026-11-13 | Suites, test cases, statuses, durations, failures, skipped cases and `system-out`/`system-err`. No Gherkin steps, screenshots, traces or arbitrary attachments. JUnit XML is not a replacement for a native Playwright report; Playwright projects should use the Playwright JSON adapter. |
| Legacy JSON outlines | Flat | 2026-11-13 | Examples arrive expanded. Tolkira keeps those rows flat and does not reconstruct the original outline table. Messages outlines are grouped. |
| Rules and backgrounds in the summary | HTML only | 2026-11-13 | The version-2 JSON summary exposes a flat scenario list and inherited tags. Rules and backgrounds are an HTML presentation feature. |
| Themes and charts | Not supported | 2026-11-13 | Branding is title, metadata, logo, accent colour and dark mode. The old cucumber-html-reporter themes and charts are not reproduced. |
| External attachments | Not supported | 2026-11-19 | Output stays one file. Current limits: 100 MB total input, 50 MB per attachment, 100 MB total attachments, with a warning above 10 MB. Decision: [ADR 0006](adr/0006-inline-attachments.md). |
| Early input warning | Advisory | 2026-11-23 | Before parsing, the CLI resolves the input files once, stats them without reading content and writes one stderr line when their total is at least 50 MiB (52,428,800 bytes): `tolkira: warning: input files total 50.0 MB, at or above the 50 MB early-warning threshold; parsing and rendering may take a while.` The total is MiB arithmetic shown at one decimal and labelled MB. It is a hint, not a cap: it names no path, changes no exit code or output byte, and the 100 MB hard input cap still applies. It is written on any run that resolves large inputs, including `--json` and `--ci`-only runs. The same resolved list goes to the scan and the loader. It counts each resolved path once; identical content under two paths counts twice, so the early total can exceed the content-deduped `input` value in the post-render `--max-size` warning; both warnings can appear in one run and measure different sets. |
| History and trends | Opt-in | 2026-11-23 | `--history <file>` keeps the newest configured aggregate runs (default 30, range 1 to 365 via `--history-limit <n>`) in a schema-version-1 or -2 sidecar and adds a Trends tab from the second run. Entries hold id, recorded time, resolved title, status, counts, duration, attachment totals and the optional `flaky` count only: no scenario names, step text, paths, tags or attachment content. Entries without the count show `—` for both flaky cells. There is no scenario-level history, multi-suite grouping or dashboard, and the
CLI is the only automatic writer, so concurrent generation on one sidecar can
lose an update. A report embeds the prior-run aggregates it was generated with. |
| History window | Configurable, destructive below | 2026-11-23 | `--history-limit <n>` needs `--history`, accepts a decimal integer from 1 to 365 and defaults to 30; it bounds the runs read, appended, written and rendered in Trends. Lowering it is destructive on the next successful write: the oldest runs beyond the new window are dropped and raising the limit later cannot restore them. A maximal valid window can exceed the 1 MiB cap and lose further runs on write; the schema, cap and older-reader rules are in `docs/AGENT-INTERFACE.md` under Run history. |
| Localisation | en, de | 2026-11-20 | The report shell and the opt-in email summary take their labels and accessibility text from the active catalog; all visible counts are locale-formatted (English report digits stay raw; the email groups them), including the client. Test data, Gherkin keywords, attachment content and names, metadata and URIs render verbatim in every locale; the JSON summary and CI text stay English. `de-AT` uses `de` but keeps its `lang` tag. Only left-to-right locales ship: there is no RTL layout, pseudo-locale, localized default title or in-report language switcher. |
| Native Playwright adapter | Basic | 2026-11-22 | The Playwright JSON reporter is read natively: projects, file/describe rules, retries, nested steps, expected/unexpected outcomes, tags, annotations, inline and in-tree path attachments, `stdout`/`stderr` and run-level errors. The final attempt is the visible one. A retried scenario also shows a collapsed, report-only `Earlier attempts` block with status, duration and the first failure message for up to three executed earlier attempts (`3 of 5` when capped). A single-input report embeds at most one earlier image, from the first failed displayed earlier attempt, only when it fits a 10 MB evidence budget and the final attachments leave at least 10 MB of the 100 MB cap; multi-input reports show the block without an earlier image. Earlier evidence stays out of the summary attachment counts and bytes, the JSON/CI/email/history outputs and the search index, and an earlier probe never raises `skippedAttachments`. Expected-failure retries can show their raw earlier failures. No trace viewer or HTML-report replay is claimed; trace zip attachments are skipped. Path attachments that resolve outside the input file's directory and the process working directory, are missing, unreadable, not a regular file, or use a URL/UNC/device path are skipped and counted. The HTML names up to three per scenario with the reason and shows a run-level and per-scenario count notice; when HTML or a PDF is written, the CLI warning carries the count without names. Earlier evidence and trace zips are not counted. |
| Flaky visibility | Display only | 2026-11-22 | A scenario whose pickle tag set (own or inherited) includes the lowercase, exact `@flaky` tag shows a localized badge, and when at least one exists the run metadata gets a separate count such as `1 tagged @flaky`, distinct from the status counts. Feature, rule and outline-level tags badge every affected row, including every outline example, so the count can exceed the visible tag labels; a failed or unexecuted tagged scenario also counts. The badge and count are report-only (HTML/PDF), not a computed flake rate or detection, and do not appear in the JSON summary, CI or email; the scenario keeps its existing status everywhere. The history sidecar adds an optional per-run `flaky` count and Trends shows `Flaky` and `Flaky share` from executed, non-skipped tagged or passed-after-retry scenarios; a positive share below 0.1% renders `<0.1%`, entries without the count show `—` for both cells, and a note explains the tag-or-retry proxy. This is a flagged share, not a flake probability. There is no flaky status, no retry trend or history, no extra summary field and no separate filter; earlier-attempt evidence is report-only and bounded as described in the Playwright row. The existing tag filter still selects `@flaky`. |
| Browser and accessibility coverage | Ongoing | 2026-11-13 | Chromium, Firefox and WebKit at 320, 390, 768, 1024 and 1440 px, plus 320 px at 200 % text zoom. This is not a formal WCAG audit. |
| Print and PDF | Browser print plus opt-in PDF | 2026-11-20 | With JavaScript, printing includes Report, Details and Trends when present and opens every detail; the screen state returns where the browser fires `afterprint`, and a missed event cannot stack panels because the reveal is print-scoped. Without JavaScript only the active Report prints and closed details stay closed. An active search or filter carries into print and narrows the Report view. Interactive chrome and video/audio attachments do not print; very wide matrices may need landscape; the browser's headers/footers, URL and page numbers stay user-controlled (the footer can reveal a local path). `--pdf <file>` prints the same complete archive through the optional Playwright Chromium engine: A4 portrait via `format: 'A4'`, 12 mm print CSS margins, `printBackground`, no header/footer/URL/page number, Chromium-only, no CLI filter state (a fresh page), no PDF-only logo/Trends, no Letter/custom paper. HTTP(S) images in caller HTML are aborted; inline data URIs render. It needs `playwright-core` (about 13 MB) plus the Chromium headless shell (285.8 MB unpacked) and helpers (about 4 MB; ffmpeg/winldd; roughly 303 MB unpacked total; the full Chromium build is not required), installed in the project where Tolkira runs; a missing engine exits 1 with the install command. `page.pdf` has no timeout option and there is no 30 s browser print default: `setContent` gets the load timeout and an explicit deadline bounds the font/image wait and the print (default five minutes; `--pdf-timeout`/`PdfOptions.timeoutMs` override it). The default Chromium launch keeps `chromiumSandbox: false`; the CSP and escaped attachments are the boundary, so run untrusted attachments in a container or VM (B-029). There is no separate PDF size cap. A print button, repeated print title, custom page-number control, tagged PDF and per-page header remain absent. Volume measured on the maintainer's machine (Chromium, 2026-11-20), not CI: 2,000 scenarios take about 5 s and produce about 670 A4 pages, 4,000 about 21 s, and 10,000 about 2.7 min and about 3,337 pages; CI can be slower, so raise `--pdf-timeout`. There is no print cap beyond the normal 10 MB size warning: clear filters for the whole run, and use the failures-only filter for large suites. Sparse attachment-only content can leave nearly empty pages, a known cosmetic limit. The PDF is not byte-identical across engine, font or OS versions. |
| Email summary | Opt-in | 2026-11-20 | `--email <file>` writes one self-contained HTML mail body from the summary; without the flag no email file exists. It has no SMTP, sending, scheduling, recipients, `.eml` draft, logo, image, `--meta` content or redaction mode, and no hidden preheader in this slice (deferred). It lists the first five failed scenarios in summary order (fixed cap), not the five slowest, counts inline attachments only, and names the report by basename or says that no full report is attached. The heading, note and failed names wrap anywhere and displayed names are capped at 200 characters; English digits are grouped (`8,509 bytes`) and durations are human (`12 ms`, `12.3 s`, `1 min 5 s`, `1 h 2 min`). A standard summary stays under 100 KB. Browser preview at 600 and 320 px is tested; Gmail/Outlook/Apple Mail rendering, clipping and image blocking are not covered, and the HTML body cannot set a mail subject. |
