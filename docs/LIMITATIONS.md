# Limitations

Last verified: **2026-11-24**. "Verified" means the repository state on that
date: the cited fixture or test exists and passes. It does not mean every
producer was re-run on that date.

| Area | Status | Last verified | What it means |
| --- | --- | --- | --- |
| Behave 1.3.3 | Partial | 2026-11-19 | Real runs (`behave-real.json`, `behave-real-attachments.json`) cover pass/fail/error statuses, seconds-based durations, a multiline doc string, a data table, a multiline error message and an inline PNG. The recorded rich run contains one `error` status; `hook_error` and `cleanup_error` are covered by synthetic tests. Behave's formatter omits error text for `error` and `hook_error` step results; `cleanup_error` is recorded on the scenario/feature during context cleanup and is accepted defensively in a step result. Dry-run/WIP statuses (`untested`, `untested_pending`, `untested_undefined`, `pending_warn`) and `xfailed`/`xpassed` are unsupported, and scenario-level hook failures without a step result are not reconstructed. |
| JUnit XML | Basic | 2026-11-13 | Suites, test cases, statuses, durations, failures, skipped cases and `system-out`/`system-err`. No Gherkin steps, screenshots, traces or arbitrary attachments. JUnit XML is not a replacement for a native Playwright report; Playwright projects should use the Playwright JSON adapter. |
| Legacy JSON outlines | Flat | 2026-11-13 | Examples arrive expanded. Tolkira keeps those rows flat and does not reconstruct the original outline table. Messages outlines are grouped. |
| Messages `attempt` | Validated | 2026-11-24 | `testCaseStarted.attempt` is optional; when present it must be a non-negative safe integer, otherwise the input fails with the existing line error naming the file, line and `testCaseStarted.attempt`. An absent attempt is 0 in the report model and the summary, and `--json` never contains `null` for it. |
| Legacy compat bad arrays | `ignoreBadJsonFile` | 2026-11-24 | With `ignoreBadJsonFile: true`, a `jsonDir` file whose JSON is not an array of legacy feature objects, such as `[1,2,3]` or an array of non-feature objects, is skipped with the existing skipped-file warning and is not merged into the report or the sidecar. Without the flag the same file fails with the compat legacy-array error. Both compat checks use the same feature-shape predicate as `detectInput`; a valid feature array still merges. |
| Rules and backgrounds in the summary | HTML only | 2026-11-13 | The version-2 JSON summary exposes a flat scenario list and inherited tags. Rules and backgrounds are an HTML presentation feature. |
| Themes and charts | Not supported | 2026-11-13 | Branding is title, metadata, logo, accent colour and dark mode. The old cucumber-html-reporter themes and charts are not reproduced. |
| External attachments | Not supported | 2026-11-19 | Output stays one file. Current limits: 100 MB total input, 50 MB per attachment, 100 MB total attachments, with a warning above 10 MB. Decision: [ADR 0006](adr/0006-inline-attachments.md). |
| Early input warning | Advisory | 2026-11-23 | Before parsing, the CLI resolves the input files once, stats them without reading content and writes one stderr line when their total is at least 50 MiB (52,428,800 bytes): `tolkira: warning: input files total 50.0 MB, at or above the 50 MB early-warning threshold; parsing and rendering may take a while.` The total is MiB arithmetic shown at one decimal and labelled MB. It is a hint, not a cap: it names no path, changes no exit code or output byte, and the 100 MB hard input cap still applies. It is written on any run that resolves large inputs, including `--json` and `--ci`-only runs. The same resolved list goes to the scan and the loader. It counts each resolved path once; identical content under two paths counts twice, so the early total can exceed the content-deduped `input` value in the post-render `--max-size` warning; both warnings can appear in one run and measure different sets. |
| Input accounting | Loaded files only | 2026-11-24 | In the core loader, `inputFiles` and `inputBytes` count only files that produce a loader group, including a validation-only file with no envelopes. A `skip` decision, a duplicate content hash and an empty `.jsonl`/`.ndjson` shard skipped by a directory scan create no group and do not count toward either value or the 100 MB total cap. The per-file 100 MB guard runs before the read; the total cap applies to unique loaded content after dedupe and skip and fails with `Inputs exceed 100 MB in total. Split the run into smaller inputs or reduce the attachment payload.` The 50 MiB early warning still measures every resolved path and can differ. A directory of many large skipped files still spends read time, because the content must be read to recognise a skip; there is no aggregate cap beyond the per-file guard. The compatibility shim's own pre-read accounting is separate. |
| Empty Messages shards | Scanned only | 2026-11-24 | A directory scan skips a `.jsonl`/`.ndjson` file with zero non-empty lines after an optional BOM and whitespace, without a loader group, input count or warning. An explicitly named zero-byte or whitespace-only file still fails with `Input is empty: <file>`; a directory with only empty shards fails with `No supported report files found.`; a non-empty malformed shard keeps its line error. No option changes this. |
| History and trends | Opt-in | 2026-11-23 | `--history <file>` keeps the newest configured aggregate runs (default 30, range 1 to 365 via `--history-limit <n>`) in a schema-version-1 or -2 sidecar and adds a Trends tab from the second run. Entries hold id, recorded time, resolved title, status, counts, duration, attachment totals and the optional `flaky` count only: no scenario names, step text, paths, tags or attachment content. Entries without the count show `—` for both flaky cells. There is no scenario-level history, multi-suite grouping or dashboard, and the
CLI is the only automatic writer, so concurrent generation on one sidecar can
lose an update. A report embeds the prior-run aggregates it was generated with. |
| History window | Configurable, destructive below | 2026-11-23 | `--history-limit <n>` needs `--history`, accepts a decimal integer from 1 to 365 and defaults to 30; it bounds the runs read, appended, written and rendered in Trends. Lowering it is destructive on the next successful write: the oldest runs beyond the new window are dropped and raising the limit later cannot restore them. A maximal valid window can exceed the 1 MiB cap and lose further runs on write; the schema, cap and older-reader rules are in `docs/AGENT-INTERFACE.md` under Run history. |
| Baseline comparison | Opt-in | 2026-11-24 | `--baseline <file>` reads one earlier schema-2 `--json` summary, read-only and never rewritten, and adds a report panel, row badges, a summary `baseline` block with per-scenario `change` and one Markdown CI line. It needs `--out`, `--pdf`, `--json` or `--ci markdown`; email-only and GitHub/Azure-only runs are usage errors. The reader caps the file at 10 MiB (10,485,760 bytes), checks the descriptor for a regular file, strips a BOM and rejects prototype keys, deep nesting and malformed entries. Identity is feature name + scenario name, then the positional outline example coordinate when every row on both sides carries it, then display URI for the genuinely unmatched remainder; a group that cannot be reduced to unique rows is ambiguous and makes no claim. New failure means the row fails now and did not fail in the baseline, including a scenario new to the suite; there is no separate regressed class. Not in this run means absent from this summary (deleted, never started, filtered or another shard), not a claim of deletion. There is no automatic baseline writer, scenario-level history, run store, first/last-seen or fail-streak trend. The report and summary embed baseline feature/scenario names and URIs, never the baseline path; the file has no title or timestamp, so link the two artifacts by command. The example coordinate is positional, so inserting or reordering an Examples row can mispair a later row. Use one baseline per suite and variant and the merged run for shards; a wrong baseline produces spurious counts, not a crash. `renderHtml` and `CucumberHtmlStream` do not take a baseline in 0.6.0. Keep the baseline path separate from the current `--json` redirect. |
| Localisation | en, de | 2026-11-20 | The report shell and the opt-in email summary take their labels and accessibility text from the active catalog; all visible counts are locale-formatted (English report digits stay raw; the email groups them), including the client. Test data, Gherkin keywords, attachment content and names, metadata and URIs render verbatim in every locale; the JSON summary and CI text stay English. `de-AT` uses `de` but keeps its `lang` tag. Only left-to-right locales ship: there is no RTL layout, pseudo-locale, localized default title or in-report language switcher. |
| Native Playwright adapter | Basic | 2026-11-24 | The Playwright JSON reporter is read natively: projects, file/describe rules, retries, nested steps, expected/unexpected outcomes, tags, annotations, inline and in-tree path attachments, `stdout`/`stderr` and run-level errors. The final result is the visible one: the last result in array order wins when `retry` is missing or equal, and the highest retry wins otherwise; a full attempt and timestamp tie between two starts selects the later start. With no usable start timestamp the report omits the run date instead of showing 1970-01-01. A test is skipped only when its final result is skipped or it is marked skipped with no result; a failed final result wins over an expected skip, and a passed final result under an expected skip is an unexpected pass (failed). A spec without `file` uses the enclosing suite's file for its scenario URI and rule name; an explicit spec `file` wins, and without a project the feature name follows that inherited file, while a project stays the feature grouping. A retried scenario also shows a collapsed, report-only `Earlier attempts` block with status, duration and the first failure message for up to three executed earlier attempts (`3 of 5` when capped). A single-input report embeds at most one earlier image, from the first failed displayed earlier attempt, only when it fits a 10 MB evidence budget and the final attachments leave at least 10 MB of the 100 MB cap; multi-input reports show the block without an earlier image. Earlier evidence stays out of the summary attachment counts and bytes, the JSON/CI/email/history outputs and the search index, and an earlier probe never raises `skippedAttachments`. Expected-failure retries can show their raw earlier failures. No trace viewer or HTML-report replay is claimed; trace zip attachments are skipped. Path attachments that resolve outside the input file's directory and the process working directory, are missing, unreadable, not a regular file, or use a URL/UNC/device path are skipped and counted. The HTML names up to three per scenario with the reason and shows a run-level and per-scenario count notice; when HTML or a PDF is written, the CLI warning carries the count without names. Earlier evidence and trace zips are not counted. |
| Flaky visibility | Display only | 2026-11-22 | A scenario whose pickle tag set (own or inherited) includes the lowercase, exact `@flaky` tag shows a localized badge, and when at least one exists the run metadata gets a separate count such as `1 tagged @flaky`, distinct from the status counts. Feature, rule and outline-level tags badge every affected row, including every outline example, so the count can exceed the visible tag labels; a failed or unexecuted tagged scenario also counts. The badge and count are report-only (HTML/PDF), not a computed flake rate or detection, and do not appear in the JSON summary, CI or email; the scenario keeps its existing status everywhere. The history sidecar adds an optional per-run `flaky` count and Trends shows `Flaky` and `Flaky share` from executed, non-skipped tagged or passed-after-retry scenarios; a positive share below 0.1% renders `<0.1%`, entries without the count show `—` for both cells, and a note explains the tag-or-retry proxy. This is a flagged share, not a flake probability. There is no flaky status, no retry trend or history, no extra summary field and no separate filter; earlier-attempt evidence is report-only and bounded as described in the Playwright row. The existing tag filter still selects `@flaky`. |
| Browser and accessibility coverage | Ongoing | 2026-11-13 | Chromium, Firefox and WebKit at 320, 390, 768, 1024 and 1440 px, plus 320 px at 200 % text zoom. This is not a formal WCAG audit. |
| Print and PDF | Browser print plus opt-in PDF | 2026-11-20 | With JavaScript, printing includes Report, Details and Trends when present and opens every detail; the screen state returns where the browser fires `afterprint`, and a missed event cannot stack panels because the reveal is print-scoped. Without JavaScript only the active Report prints and closed details stay closed; `--static` prints the all-expanded stacked form without scripts. An active search or filter carries into print and narrows the Report view. Interactive chrome and video/audio attachments do not print; very wide matrices may need landscape; the browser's headers/footers, URL and page numbers stay user-controlled (the footer can reveal a local path). `--pdf <file>` prints the same complete archive through the optional Playwright Chromium engine: A4 portrait via `format: 'A4'`, 12 mm print CSS margins, `printBackground`, no header/footer/URL/page number, Chromium-only, no CLI filter state (a fresh page), no PDF-only logo/Trends, no Letter/custom paper. HTTP(S) images in caller HTML are aborted; inline data URIs render. It needs `playwright-core` (about 13 MB) plus the Chromium headless shell (285.8 MB unpacked) and helpers (about 4 MB; ffmpeg/winldd; roughly 303 MB unpacked total; the full Chromium build is not required), installed in the project where Tolkira runs; a missing engine exits 1 with the install command. `page.pdf` has no timeout option and there is no 30 s browser print default: `setContent` gets the load timeout and an explicit deadline bounds the font/image wait and the print (default five minutes; `--pdf-timeout`/`PdfOptions.timeoutMs` override it). The default Chromium launch keeps `chromiumSandbox: false`; the CSP and escaped attachments are the boundary, so run untrusted attachments in a container or VM (B-029). There is no separate PDF size cap. A print button, repeated print title, custom page-number control, tagged PDF and per-page header remain absent. Volume measured on the maintainer's machine (Chromium, 2026-11-20), not CI: 2,000 scenarios take about 5 s and produce about 670 A4 pages, 4,000 about 21 s, and 10,000 about 2.7 min and about 3,337 pages; CI can be slower, so raise `--pdf-timeout`. There is no print cap beyond the normal 10 MB size warning: clear filters for the whole run, and use the failures-only filter for large suites. Sparse attachment-only content can leave nearly empty pages, a known cosmetic limit. The PDF is not byte-identical across engine, font or OS versions. |
| Static report | Opt-in | 2026-11-24 | `--static` (API `static: true`) writes one script-free, all-expanded report and needs `--out` or `--pdf`. It removes the tab bar, search/status/tag filters, copy-failure and log-copy buttons, lightbox and image buttons; opens every `<details>`; stacks Report, Details and Trends (Trends only with two or more runs); keeps exactly one `<main>` around the three view IDs; and prints/PDFs every present section. A bookmarked `?query=`/`?hide=`/`?tag=` URL shows the full report because no script restores it. It does not repair CSS or `data:` images blocked by a host CSP, does not restore scripts, has no auto-detection and does not change the report's content; the default and static forms both render exactly one `<main>` around Report, Details and Trends, with the site header as the only banner (B-048). A default report with two or more history runs gains the Trends shell CSS. |
| Email summary | Opt-in | 2026-11-20 | `--email <file>` writes one self-contained HTML mail body from the summary; without the flag no email file exists. It has no SMTP, sending, scheduling, recipients, `.eml` draft, logo, image, `--meta` content or redaction mode, and no hidden preheader in this slice (deferred). It lists the first five failed scenarios in summary order (fixed cap), not the five slowest, counts inline attachments only, and names the report by basename or says that no full report is attached. The heading, note and failed names wrap anywhere and displayed names are capped at 200 characters; English digits are grouped (`8,509 bytes`) and durations are human (`12 ms`, `12.3 s`, `1 min 5 s`, `1 h 2 min`). A standard summary stays under 100 KB. Browser preview at 600 and 320 px is tested; Gmail/Outlook/Apple Mail rendering, clipping and image blocking are not covered, and the HTML body cannot set a mail subject. |
